# 截图评审模式

> 用于静态视觉审查。只判断当前画面能够证明的内容，不执行页面交互，也不把截图推断包装成 E2E 结论。

## 进入条件

输入是截图、本地图片或录屏中的指定静态帧，目标是快速发现桌面端信息层级、空间利用、比例、遮挡、溢出和视觉一致性问题。连续录屏可以补充可见变化的时序证据，但仍不能替代当前运行态、DOM、Console 或 Network 的实测。

如果用户同时提供 URL，也只有在明确要求实测时才切换到“全站交互 E2E 走查”。静态评审阶段不要点击页面来混合证据。

## 一、登记证据边界

1. 记录截图对应的页面、已知视口、缩放比例和状态；未知项明确写“未知”。
2. 区分截图直接可见事实、用户补充的产品事实和运行态未知项。
3. 截图只能证明捕获时刻的画面，不能证明按钮可用、键盘行为、焦点顺序、动画、请求结果或修复已经生效。

## 二、先扫主矛盾

按以下顺序观察，先处理控制整屏体验的问题：

1. 最大的内容元素是否挤压核心任务。
2. 最大的无效空白是否来自不合理的固定区域或宽度分配。
3. 最小、最难读的文字是否与媒体、卡片或控件比例失衡。
4. 固定侧栏、顶栏、底部输入区或检查器是否长期侵占工作区。
5. 孤立入口是否在尺寸、描边、对齐、分组和语义上脱离同层级控件。

再按 [desktop-review-rubric.md](desktop-review-rubric.md) 检查当前画面可见的页面结构、浮层边界、桌面密度和状态表达。不要用无法从画面验证的键盘、关闭或网络条目定性。

## 三、判定问题

每个问题包含：

| 字段 | 要求 |
|---|---|
| 位置 | 页面区域或可见控件 |
| 画面事实 | 只写截图中能指出的现象 |
| 影响 | 对识别、阅读、操作效率或一致性的影响 |
| PC 预期 | 可观察的桌面端结果，不锁死实现 |
| 严重度 | P0–P3 |
| 置信度 | 高 / 中 / 低，并说明证据限制 |

无法确认交互时，不写“点击无效”“无法关闭”或“请求失败”。改写为可交接的待验证项：

1. **验证问题**：具体要确认什么。
2. **验证动作**：点击、键盘、调整视口或查看运行日志的步骤。
3. **判定标准**：什么结果算通过，什么结果算失败。

## 四、输出

1. 一句话结论，明确这是静态截图评审及其证据范围。
2. 按影响排序的 5–10 个问题；证据不足时宁缺毋滥。
3. 最值得先改的 3 项，主导比例和空间问题优先。
4. 可直接交给 E2E 走查的待验证清单。

截图评审到此结束。除非任务明确进入下一阶段，不执行点击遍历、Console/Network 检查或回归判定。
