# PC Web 评审反馈闭环

> 把用户对评审结果的明确纠正转成可追踪、可复用、能够改变下次行为的规则。

## 使用时机

- **每次开始评审时**：先依据主 Skill 独立完成视觉主矛盾扫描，再读取“当前生效规则”补漏；不要先读历史案例。
- **收到用户反馈后**：读取本文和
  [review-feedback-cases.md](review-feedback-cases.md)，完成差距归类、案例追加和规则更新。
- **没有用户明确反馈时**：只应用规则，不自行追加案例。

历史反馈是观察提示，不是当前产品事实。不得因为旧案例出现过某个问题，就在新截图中无证据复述。

## 自更新流程

### 步骤一：拆分证据等级

把反馈中的信息拆成三类：

1. **截图或录屏可见事实**：可以直接进入视觉评审，但仍标注置信度。
2. **用户确认的产品事实**：例如用户明确说明“左侧栏没有收起功能”；记录为“用户确认”，不要伪装成截图发现。
3. **运行态未知项**：例如无法从截图判断右栏是否始终为空；转成明确的验证问题、动作和判定规则。

### 步骤二：比较上一版结果

每个反馈点只能归入一个主要类别：

| 类别 | 定义 |
|---|---|
| 命中 | 上一版明确指出同一问题、影响和正确方向，且优先级合理 |
| 部分命中 | 提到了相关现象，但遗漏根因、具体区域、验证交接或优先级不足 |
| 漏评 | 上一版没有覆盖该问题 |
| 过度推断 | 证据不足却写成已确认事实，或给出超出证据的结论 |
| 优先级偏差 | 问题可能成立，但挤占了更主导问题的位置 |

### 步骤三：只提升可泛化规则

一条反馈要进入“当前生效规则”，必须同时满足：

1. 能用于多个 PC Web 产品或页面。
2. 能改变观察顺序、证据表达、问题优先级或验证动作。
3. 不依赖某个产品名称、内部实现或一次性的页面数据。

仅适用于特定产品的问题写入对应产品基线。涉及私有或带公司属性的信息不得写入共享 Skill。

### 步骤四：追加案例

在 [review-feedback-cases.md](review-feedback-cases.md) 末尾追加案例，至少记录：

- 日期和证据；
- 用户反馈摘要；
- 命中、部分命中、漏评、过度推断和优先级偏差；
- 新增或调整的规则 ID；
- 下次如何验证规则真正生效。

保留用户原意，但使用概括表述；不要复制敏感信息、令牌或无关上下文。

### 步骤五：更新和淘汰规则

- 新规则使用递增 ID：`FR-001`、`FR-002`。
- 规则含义变化时，在案例中记录原因，再修改本文。
- 两次以上反馈证明规则导致误报时，将其移入“已停用规则”，不要直接删除历史。
- 规则重复时合并，不为同一件事堆叠近义检查项。

## 当前生效规则

### FR-001：先检查主内容的比例关系

第一轮先找出最大内容元素、最大无效空白、最小文字、最长占位区域和最孤立控件。在检查文字细节前，比较图片、视频、代码块、文本和空白在有效工作区中的相对尺度。媒体在移动端合理，不代表原尺寸进入 PC 对话仍合理。

至少回答：

- 媒体宽高相对会话内容列是否过大；
- 正文与媒体是否形成明显的“小字配大图”；
- 大媒体是否导致单屏只能看到极少上下文；
- 问题是否可能来自移动端固定尺寸或断点缺失。

对图片结果补充方图、横图、竖图和多图场景的默认预览、放大、关闭与焦点恢复契约。截图只能说明“呈现出类似移动端尺寸直接延续的特征”；只有用户或实现证据确认后，才能把移动端适配写成事实根因。

### FR-002：逐一检查固定侧栏的价值和收起能力

对左栏、右栏、检查器等长期占位区域分别检查：

- 当前内容价值是否配得上占用宽度；
- 是否存在可见的折叠入口；
- 折叠后主工作区是否回收空间；
- 空状态是否仍强制占位；
- 折叠状态是否记忆，以及如何恢复。

截图没有出现折叠入口，只能写“截图中未见”，不能直接证明产品没有折叠能力。用户明确确认时，使用“用户确认”作为证据。

### FR-003：空面板必须区分状态问题与结构问题

看到大面积空白时，不立即断言设计错误。向调用方交接三个问题：

1. 什么操作或数据会让面板出现内容？
2. 面板是持续保留、按任务展开，还是空时自动收起？
3. 用户能否主动关闭、折叠或调宽？

若面板长期为空、持续占宽且不可收起，判定为桌面空间利用问题；若它只在相关任务中展开且退出路径清晰，则空状态本身不构成问题。先确认状态模型，再选择自动收起、手动折叠或默认窄态，不要从单张截图锁定唯一方案。

### FR-004：孤立图标也要纳入视觉一致性评审

对单独出现的加号、返回、更多等图标，比较其尺寸、描边、容器、对齐、留白和邻近关系。不能只写“难看”，必须说明它与同层级控件如何不一致，以及这种不一致是否造成错误分组、抢夺注意力或入口难以理解。真实功能、Tooltip 和可访问名称无法从截图确认时，作为运行态复核项交接。

### FR-005：主导比例问题优先于局部微观问题

排序“最值得先改”时，先处理影响整屏阅读和空间分配的问题，再处理输入框高度、选中态、状态圆点等局部细节。若一个问题控制了主要视觉面积，应说明它为何主导体验。

### FR-006：待验证项必须可交接

每个未知项必须包含：

- 验证问题；
- 建议操作或需要补充的证据；
- 通过与失败的判断标准。

目标是让调用 Skill 的 Agent 可以直接继续复核，而不是收到一句无法执行的“待实测”。
