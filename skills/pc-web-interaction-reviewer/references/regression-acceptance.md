# 回归验收模式

> 用于按既定问题、验收点或 E2E Case 复跑修复结果。目标是稳定复现和判定，不进行无边界探索。

## 进入条件

开始前必须至少具备一种输入：

- 已确认问题 ID 和原复现步骤；
- 明确的验收标准；
- 可执行的 E2E Case；
- 上一轮走查形成的失败清单。

如果只有“帮我看看这个站点是否正常”而没有既定 Case，应使用 [full-site-e2e-walkthrough.md](full-site-e2e-walkthrough.md)。

读取 [desktop-review-rubric.md](desktop-review-rubric.md) 中与 Case 相关的条目，并委派 `dev-tools:browser-control` 处理 provider、登录态、安全门、账本和浏览器证据；已有自动化 Case 可委派 `web-e2e` 执行。

## 一、冻结回归范围

为每个 Case 登记：

| Case ID | 原问题 | 前置条件 | 固定步骤 | 通过标准 | 补充边界 |
|---|---|---|---|---|---|

范围规则：

1. 原路径、原视口、原数据状态和原断言优先，确保结果可比较。
2. 只补测与修复直接相关的视口、长内容、键盘、焦点和重复打开等边界。
3. 路径中观察到的新问题可以记录为“新增回归”，但不展开全站入口发现，也不把它加入本轮通过分母。
4. 需求或验收点不明确时先标记“证据不足”，不得自行放宽标准。
5. 多个可见 UI Case 必须在执行前冻结“一项一组”的截图计划；整页总览图只能补充上下文，不能代替逐 Case 证据。

## 二、逐 Case 复跑

每个 Case 独立执行：

1. 恢复已知前置状态，记录构建版本和环境。
2. 捕获动作前截图、页面状态；涉及请求或脚本行为时建立 Console/Network 增量基线。
3. 严格按固定步骤操作，不临时改用更容易成功的替代路径。
4. 捕获动作后截图、页面状态、焦点、关键 DOM/可访问性变化，以及相关 Console/Network 增量。
5. 逐条对照验收标准，不以“看起来好了”代替断言。
6. 清理本 Case 产生的临时状态，再进入下一 Case，避免相互污染。

### 逐项截图证据

当 Case 改变可见 UI 时，每个 Case 至少交付一组独立的修复前 / 修复后证据：

- 图片标题或相邻文本必须包含 Case ID 和问题名称。
- 截图应聚焦发生变化的区域，同时保留足以判断位置和状态的上下文。
- 前后图必须保持相同 CSS 视口、DPR 和页面缩放；独立裁切时使用相同视觉比例。若只能归一化素材，必须披露方法，并且不能用它判断未经归一化的尺寸、描边重量或间距优劣。
- 同一张原始截图可以作为多个 Case 的来源，但每个 Case 必须生成独立标注或独立裁切后的对比图，不能只重复引用一张整页图。
- 折叠、展开、恢复、选中等状态型 Case，至少展示能证明关键状态的画面；一组两帧不足时补第三帧或单独的状态截图。
- 孤立 fixture 只能证明组件自身样式。变更位于共享 Header、多栏边界或会随相邻动作重排时，必须再用真实页面构成验证至少一个正常视口和一个相关断点；fixture 不能证明不重叠、空间回收或真实层级。
- 交付前核对“计划可见 UI Case 数 = 独立前后截图组数”；数量不一致时，该批视觉证据判定为不完整。

## 三、判定

每个 Case 只能使用以下结果：

- **已修复**：全部既定断言有证据通过，且相关边界未出现回归。
- **仍失败**：原问题可复现，或任一关键断言失败。
- **证据不足**：环境、数据、权限或证据缺失，无法可靠判定。
- **阻断**：安全门、构建故障或外部依赖使步骤无法继续。

路径内出现与修复相关的新失败时标记“新增回归”，并单独建问题，不把原 Case 误报为已修复。自动化测试通过不是唯一证据；视觉、页面状态和必要的 Console/Network 仍要按 Case 契约核验。

## 四、输出

1. 总结论：通过 / 不通过 / 证据不足。
2. 范围：计划 Case 数、已执行、已修复、仍失败、证据不足、阻断。
3. 逐 Case 结果表：预期、实际、动作前后证据和失败原因；可见 UI Case 逐项链接自己的前后截图组。
4. 新增回归清单；只记录复跑路径中有证据的问题。
5. 未覆盖项及恢复验收所需条件。

只有所有计划 Case 均为“已修复”时才可判定本轮通过。不得把未执行、阻断或证据不足写成通过，也不得用回归验收名义扩展为全站探索。

## 五、PR 交付与合并门

任务包含创建 PR、更新 PR 或合并时，证据文件存在于仓库或聊天中不等于已经交付。必须检查实际渲染的 PR 正文，并满足：

1. 正文声明 `Visible UI cases: N`，并包含 `Case ID → 问题 → 修复前 → 修复后` 证据矩阵。
2. 每个可见 UI Case 在自己的行或小节中直接嵌入一组图片。可使用两张独立图片，也可使用一张清楚标注前后的同尺度对比图；仅链接报告、附件目录或总览图不计数。
3. `N = 证据矩阵中的可见 Case 数 = 独立前后截图组数`。一张总览或 contact sheet 不能重复计入多个 Case。
4. 图片使用不可变 commit SHA 的仓库 URL 或 GitHub 上传附件；不得依赖合并后会删除的功能分支名。创建或更新 PR 后，从实际 PR 页面逐项确认图片能渲染。
5. 独立验收 Agent 检查的是实际 PR 正文和图片，而不是生产者的本地报告。缺组、错配、重复占位或失效链接一律判定“视觉证据不完整”。
6. 测试、typecheck、自动化 E2E 与 OTA 通过都不能覆盖这个门。矩阵不完整时不得合并。

推荐正文结构：

```markdown
Visible UI cases: 2

| Case | 问题 | 修复前 | 修复后 |
| --- | --- | --- | --- |
| PC-001 | 左栏无法收起 | ![PC-001 before](稳定图片 URL) | ![PC-001 after](稳定图片 URL) |
| PC-002 | 右栏空置 | ![PC-002 before](稳定图片 URL) | ![PC-002 after](稳定图片 URL) |
```

如果使用一张前后拼接图，把该图嵌入对应 Case 小节，并在标题或图片内明确标注 Before / After；矩阵仍须为每个 Case 提供唯一图片组。
