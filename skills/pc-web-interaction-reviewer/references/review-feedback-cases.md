## FB-2026-07-31-001：宽屏会话页的比例、侧栏与孤立图标

- **证据**：单张 PC 宽屏截图、上一版截图评审、用户后续确认与补充。
- **用户反馈摘要**：
  - 对话中的图片相对文字过大，整体比例失调；用户提供的产品背景是该问题来自移动端适配到 PC 后没有正确缩放。
  - 用户确认左侧栏没有收起功能；更合适的方案是在侧栏提供明确按钮并回收主区空间。
  - 右侧栏空白过多，但截图无法判断它是否长期为空、为何为空以及是否能收起；评审应把这些问题交给调用方继续核验。
  - 顶部孤立的加号图标与整体界面不协调。
- **命中**：
  - 上一版发现右侧空面板持续占宽，以及三栏空间分配没有围绕核心会话任务。
  - 上一版提出左右栏应可折叠或调宽。
  - 上一版最终把“左右栏能否折叠”保留为待测项，没有仅凭截图断言产品行为。
- **部分命中**：
  - 上一版在待测项中提到左右栏能否折叠，但没有把左栏和右栏分别建立证据：左栏后来由用户确认为不可收起，右栏仍属于运行态未知。
  - 上一版指出会话区存在大量空白，但没有识别图片与文字之间的主导比例失衡。
  - 上一版提到聊天内容和图片受到三栏挤压，也指出文字可读性，但没有把“大图、小字、单轮内容过高”组合成核心比例问题。
- **漏评**：
  - 未指出对话图片过大、文字相对过小，以及可能存在移动端媒体尺寸未针对 PC 缩放的问题。
  - 未评审顶部加号图标在尺寸、对齐、分组和视觉语言上的不一致。
  - 未把右栏“为什么为空、何时有内容、能否收起”写成可直接交给调用方执行的验证任务。
  - 未提供方图、横图、竖图、多图以及大图预览关闭后的媒体专项 E2E 契约。
- **过度推断**：
  - 上一版使用“固定宽度”并直接给出自动收起预期；截图只能证明它当前占据稳定的一栏，不能证明 CSS 固定宽度、始终为空或完全没有收起能力。
  - 空输入框偏高是截图事实，但现有输入框是否会自增长仍需运行态确认。
- **优先级偏差**：
  - 输入框高度、选中态和状态圆点可能值得检查，但不应排在主媒体比例和固定侧栏问题之前。
- **规则变化**：新增 `FR-001` 至 `FR-006`。
- **下次生效检查**：
  - 截图含大媒体时，前 3 个问题中应出现媒体与文字/工作区的比例判断，或明确说明比例合理。
  - 固定侧栏必须逐栏记录内容价值、可见收起入口和证据等级。
  - 未知的空面板状态必须输出验证问题、动作和判定标准。
  - 孤立图标至少经过一次同层级视觉一致性检查。
  - 正式评审前先找出最大元素、最大无效空白、最小文字、最长占位区域和最孤立控件，再进入通用检查表。

## FB-2026-07-31-002：URL 登录态被错误推断

- **证据**：一次 URL 交互评审的浏览器路由记录，以及用户随后对登录态前提的明确纠正。
- **用户反馈摘要**：
  - 用户清楚目标链接需要复用当前 Chrome 的已有登录态。
  - Agent 未询问用户，直接把链接归入无登录态槽位，导致可用的现有 Chrome 被排除。
  - 登录态不明确时应先询问，并在本地记录每次判断，避免再次靠 URL 外观猜测。
- **命中**：
  - 原有 `browser-control` 已把“是否需要已有登录态”定义为第一路由键，并要求账本记录布尔判断。
- **部分命中**：
  - 原规则提到“无法判断时询问用户”，但没有禁止把用户提供的 URL 自行解释为公开、无登录态页面。
  - 原账本记录了判断结果，却没有强制记录判断来源，也不能复用同一链接的用户确认。
- **漏评**：
  - 未把登录态歧义作为开始 E2E 前的阻断门。
  - 未在选择 provider 前询问用户是否需要复用当前 Chrome。
- **过度推断**：
  - 根据链接形式和页面用途自行写入“不需要已有登录态”，把未经确认的猜测当成路由事实。
- **优先级偏差**：
  - 在登录态前提未确定时继续探测无登录态 provider，优先级高于了本应先完成的用户确认。
- **规则变化**：新增 `FR-007`；`browser-control` 新增登录态确认门、判断来源校验和本地 URL 指纹注册表。
- **下次生效检查**：
  - 用户只提供 URL、未说明登录态且两种选择会改变结果时，必须先查询本地精确记录；未命中则询问用户。
  - 本轮账本必须同时包含“是否需要已有登录态”和合法的判断来源。
  - 用户当前确认必须覆盖本地旧记录；任何本地文件都不得保存原始 URL。

## FB-2026-07-31-003：空状态走查遗漏活跃三栏工作区

- **证据**：一张 PC 活跃会话宽屏截图、上一轮全站走查覆盖记录，以及用户对功能和交互的明确补充。
- **用户反馈摘要**：
  - 图标式全局模式入口只有符号，普通用户难以理解用途、当前状态和退出逻辑。
  - 用户确认左侧持久栏无法收起。
  - 用户确认右侧区域当前为空、移动端对应位置提供快捷指令集合，PC 端也需要独立收起能力。
- **命中**：
  - 既有规则已经要求逐栏检查收起能力、区分空面板状态与结构、复核孤立图标。
- **部分命中**：
  - 上一版提到侧栏空间与空白，但没有在活跃会话状态逐栏建立用途、内容、收起和恢复证据。
  - 上一版把孤立图标主要作为视觉一致性问题，没有把全局模式的用途、启用状态和退出路径作为一个完整发现性契约。
- **漏评**：
  - 未识别图标式全局模式对新用户不可解释。
  - 未确认左栏不能收起，也未把左右栏作为两个独立能力验证。
  - 未核对右侧快捷指令在不同断点间的核心能力一致性。
- **过度推断**：
  - 只覆盖登录后空状态和静态页面后仍声称全站走查完成；没有进入用户实际工作的活跃动态详情状态。
- **优先级偏差**：
  - 路由和入口数量被放在状态覆盖之前，导致核心任务工作区缺席却没有阻止“完成”结论。
- **规则变化**：
  - 强化 `FR-002` 的逐栏独立证据和空间回收要求。
  - 强化 `FR-003` 的跨断点核心能力对照。
  - 强化 `FR-004` 的全局模式发现性、状态和退出契约。
  - 新增 `FR-008`，用页面 × 状态矩阵约束全站完成声明。
- **下次生效检查**：
  - 用不含预期答案的原始多栏工作区截图做盲测，评审应主动盘点每一栏和孤立模式入口。
  - 全站走查只有在代表性活跃详情或工作台状态已覆盖时才能判定完成；不可达时必须降为证据不足。
  - 有移动端、窄屏或用户确认的功能对照时，PC 评审必须检查核心能力是否保留。

## FB-2026-07-31-004：六项可见修复只交付一组整页前后图

- **证据**：包含 6 个可见 UI Case 的回归报告、其中唯一一组整页前后截图，以及用户对截图数量和颗粒度的明确纠正。
- **用户反馈摘要**：
  - 6 项问题不应只用一组整页前后图证明。
  - 每项变化都应有自己的前后对比，便于在 PR 中直接核对。
- **命中**：
  - 原回归规则已经要求逐 Case 捕获动作前后状态，并在结果表中附证据。
- **部分命中**：
  - 报告列出了 6 个 Case，也保存了修复前和修复后整页截图，但没有把截图与各 Case 一一绑定。
- **漏评**：
  - 没有在交付前比较“可见 UI Case 数”和“独立截图组数”。
  - 没有区分总览截图与逐项验收截图的用途。
- **过度推断**：
  - 用一组整页截图支持“完整截图与评审报告”，使证据完整性结论超出了实际截图颗粒度。
- **优先级偏差**：
  - 自动化通过与整体页面总览优先于逐项可审核性，导致 PR 阅读者不能快速确认每个问题的前后变化。
- **规则变化**：
  - 新增 `FR-009`。
  - 回归验收模式新增“一项一组”的截图计划、状态帧和数量一致性门。
- **下次生效检查**：
  - 输入 4 个可见 UI Case 时，交付物应包含 4 组独立前后证据；整页总览不计入这 4 组。
  - 同一张基线截图可被多次裁切，但每组必须清楚标明 Case ID、问题和变化区域。
  - 缺少任一截图组时，评审只能写“自动化通过、视觉证据不完整”，不能写完整验收通过。
