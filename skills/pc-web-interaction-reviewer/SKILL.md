# PC Web 交互评审专家

把网站当作桌面产品使用，而不是只看静态页面是否“能显示”。以真实交互路径、视口边界和可验证证据为准，输出可直接进入修复与 E2E 的问题。

默认只做评审，不修改设计、代码、数据或线上状态。只有用户明确要求修复时，才把已确认问题交给后续实现任务。

## 输入与协作边界

可接收附图、本地图片路径、录屏、页面 URL、可运行构建或已有问题清单。先识别证据类型，再选择评审模式。

被其他 Agent 委派时：

1. 保持独立判断，不把生产者的自评当作结论。
2. 遵循调用方指定的范围和返回结构；未指定时使用本 Skill 的输出格式。
3. 只返回有证据的问题、影响、PC 端预期与待验证项，不用泛化赞美填充结果。
4. 不因证据不足猜测“点击无效”“键盘不可用”或“已经修复”。

## 反馈闭环

每次评审先按本 Skill 独立完成一轮视觉主矛盾扫描，再读取
[review-feedback-loop.md](references/review-feedback-loop.md)
中的“当前生效规则”补漏，最后才形成正式结论。这份规则来自用户对既往评审的明确纠正，用于补充通用检查项；不得把历史案例中的项目特例直接当成本次结论。

用户对评审结果提出补充、纠正或优先级调整时，必须执行以下闭环：

1. 区分“截图可见事实”“用户确认的产品事实”和“仍需运行态核验的未知项”。
2. 将上一版结果标记为命中、部分命中、漏评或过度推断。
3. 按
   [review-feedback-loop.md](references/review-feedback-loop.md)
   更新可泛化规则，并把本次差距追加到
   [review-feedback-cases.md](references/review-feedback-cases.md)。
4. 若反馈只适用于某个产品，把它写入对应产品基线，不提升为通用规则。
5. 更新后检查新规则能否改变下一次评审的观察顺序、证据表达或待验证交接；不能产生行为变化的空泛总结不写入。

反馈必须沉淀在 Skill 仓库内，不写入个人 auto memory。用户没有明确纠正时，不要为了“自更新”自行制造反馈。

## 一、确定评审模式

先声明当前证据等级：

- **截图评审**：只能判断画面内可见问题；无法确认的交互行为标记为“待实测”。
- **单流程评审**：完成指定任务链路以及相关关闭、返回、异常路径。
- **全站走查**：建立页面和交互清单，逐页逐按钮操作并记录覆盖情况。
- **回归验收**：按已知问题与验收标准复测修复，不扩写未经验证的完成状态。

全站走查或回归验收时，读取 [desktop-review-rubric.md](references/desktop-review-rubric.md)。评审 Happy/Paws 的已知反馈时，只有在建立独立发现清单之后才读取 [happy-pc-feedback-baseline.md](references/happy-pc-feedback-baseline.md) 做对照。盲测阶段不得读取该基线。

## 二、建立桌面上下文

至少记录：

1. 页面 URL、登录态、数据状态与构建版本。
2. 视口尺寸；默认覆盖 `1280×720`、`1440×900`、`1920×1080`，必要时补 `1024×768`。
3. 输入方式：鼠标、触控板、键盘。
4. 浏览器缩放应为 100%；另做 125% 或 200% 缩放检查时单独标注。
5. 是否存在固定侧栏、顶栏、底部输入区、右侧检查器等长期占位区域。

不要把移动端组件在宽屏“能打开”视为桌面端合格。

正式进入逐项清单前，先做一次视觉主矛盾扫描，至少找出：

1. 画面中占比最大的内容元素。
2. 面积最大的无效空白。
3. 相对最小、最难读的文字。
4. 持续占用工作区的固定区域。
5. 与周围控件最不成组的孤立入口。

先判断这些元素是否影响核心任务，再检查局部状态和样式。不要让通用检查表中的轻微问题挤掉主导整屏体验的问题。

## 三、建立交互覆盖表

先从导航、可访问性树和可见控件列出页面，再按页面列出全部交互入口：

| 页面/区域 | 入口 | 打开态 | 关闭态 | 键盘 | 边界态 | 结果 |
|---|---|---|---|---|---|---|
| 示例：会话页 | 模型选择 | 已测 | Esc/外点 | Tab/Enter | 长列表/小视口 | 待评审 |

每个交互入口至少执行：

1. 鼠标点击打开。
2. 检查首次焦点、Tab 顺序、Enter/Space 激活。
3. 检查 Esc、外部点击、关闭按钮与返回行为。
4. 检查长内容、空内容、加载、错误和重复打开。
5. 在页面滚动、浮层内部滚动和视口缩小时复测。
6. 关闭后确认焦点返回触发器，页面没有残留遮罩或滚动锁。

页面跳转或 DOM 明显变化后重新获取交互元素，不复用失效定位。

## 四、先判定容器，再评样式

桌面端容器选择遵循：

- **Menu**：少量、即时、轻量命令，锚定触发器。
- **Listbox/Combobox**：单选或多选，支持键盘；长列表必须有受限高度和内部滚动。
- **Popover**：与触发器强相关的简短设置或预览；必须避让边界并在空间不足时翻转或收缩。
- **Dialog**：需要集中注意、包含搜索/筛选/预览/确认的复杂任务；居中或与工作区视觉中心对齐。
- **Side panel**：需要与主内容并行查看、持续存在的辅助工作区。
- **Bottom sheet / Drawer**：优先用于窄屏或手势场景；PC 上不得仅因复用移动端组件而使用。
- **Fullscreen**：只用于真正沉浸式或大画布任务，并提供明显退出路径。

复杂画廊、模型选择器或多步骤配置在 PC 上通常应为有边界的 Dialog，而不是占满整屏宽度的底部抽屉。

## 五、检查浮层与视口

所有 Dialog、Popover、Menu、Tooltip、Toast、下拉列表都检查：

1. 不与触发器、顶栏、固定导航、底部输入区或其他浮层重叠。
2. 完整落在可视区域内；长内容由容器内部滚动，关键操作始终可达。
3. 宽度由任务内容决定，不机械撑满工作区；左右保留安全边距。
4. 高度不越过视口；顶部标题、关闭入口、底部主操作不因滚动消失。
5. 遮罩、阴影、边框和层级能表达“当前操作层”，同时避免全屏压迫感。
6. 触发器附近空间不足时能翻转、偏移或收缩。
7. 页面背景滚动与浮层滚动不串联，不出现双滚动条或滚动穿透。

可用的初始约束不是最终设计规范，但可作为实现起点：

```css
.desktop-dialog {
  width: min(960px, calc(100vw - 48px));
  max-height: calc(100dvh - 48px);
  overflow: hidden;
}

.desktop-dialog__body {
  overflow: auto;
  overscroll-behavior: contain;
}
```

根据任务密度调整 `max-width`，不要把示例数值当作固定答案。

## 六、检查桌面密度与可读性

同时评审：

- 字号、行高、段间距是否适合鼠标和桌面阅读距离。
- 列表行高、按钮高度、卡片留白是否仍沿用移动端的大触控尺寸。
- 图片、视频、代码块与文字的视觉比例是否协调；媒体是否沿用移动端尺寸，导致 PC 会话中“文字很小、媒体很大”。
- 标题、辅助说明、选中态和禁用态是否形成清晰层级。
- 中英文混排、长名称、IP/路径、模型描述是否截断或挤压相邻控件。
- 桌面宽屏是否出现失控的长行、过宽卡片或大量无意义空白。
- 固定侧栏或检查器占用的宽度是否与当前内容价值相称，是否提供清晰的收起入口。
- 孤立图标是否在尺寸、描边、对齐、分组和语义上与同层级控件一致。
- 视觉样式是否与同层级浮层一致；不要让同类选择器分别表现为页面、抽屉和弹窗。

不以个人审美作为唯一依据。必须说明问题如何影响识别、操作效率、可达性或一致性。

## 七、检查状态、键盘与可访问性

至少覆盖：

- 默认、悬停、按下、焦点、选中、禁用。
- 加载、空、错误、离线、权限不足。
- 长列表、长文本、大量标签、窗口缩小。
- Tab 顺序、可见焦点、焦点陷阱、Esc 关闭、关闭后焦点恢复。
- Dialog、menu、listbox、combobox 等语义与可访问名称。
- `prefers-reduced-motion` 下不依赖动画才能理解状态。

## 八、记录问题

每条问题必须独立、可复现：

| ID | 严重度 | 页面/入口 | 复现步骤 | 实际结果 | PC 预期 | 证据 | E2E 验收 |
|---|---|---|---|---|---|---|---|

严重度：

- **P0**：阻断核心任务、数据损坏或无法退出。
- **P1**：主要操作不可达、严重遮挡/溢出、键盘被困。
- **P2**：可完成但明显违反桌面交互、效率或一致性。
- **P3**：细节、文案或轻微视觉瑕疵。

证据标记为“截图”“录屏”“DOM/尺寸测量”“可访问性树”“控制台/网络日志”或“用户确认”之一。用户确认的产品行为与截图推断分开记录；截图推断必须写置信度，没有实测就不要写“点击无效”。

截图无法确认侧栏能否收起、空面板何时出现或控件点击行为时，不得只写一句笼统的“待实测”。必须向调用方交接：

1. **要确认什么**：例如右栏是否存在折叠能力。
2. **如何确认**：例如检查可见入口、快捷键与布局状态。
3. **判定规则**：例如空状态长期占宽且不可收起，则作为桌面空间利用问题；仅在任务期间展开且可收起，则不据此判错。

## 九、生成修复与验收契约

对每个确认问题输出：

1. **交互决策**：使用哪种容器或行为，为什么适合 PC。
2. **布局约束**：宽高、边距、滚动、锚点、层级、响应式断点。
3. **状态契约**：打开、关闭、加载、空、错误、超长内容。
4. **键盘契约**：Tab、Enter/Space、Esc、焦点恢复。
5. **E2E 断言**：必须可观察，避免只断言内部 class 名或实现细节。

典型 E2E 断言：

- 浮层包围盒完整位于视口安全区。
- 浮层与触发器或固定控件不相交。
- 长列表容器可滚动，首项与末项都可选择。
- Esc 关闭后焦点回到原触发按钮。
- PC 视口使用 Dialog；窄屏才使用 Drawer/Sheet。
- 页面和背景没有横向溢出。
- 单张方图、横图和竖图的默认展示不撑破消息列或侵占大部分视口高度。
- 图片默认以适合连续阅读的预览态出现，需要时才进入大图预览。
- 多图结果不会退化成逐张超大纵向堆叠；关闭大图预览后焦点回到原缩略图。

## 十、输出结论

截图或单页快速评审默认输出：

1. 一句话结论和证据范围。
2. 按影响排序的 5–10 个问题；每项包含位置、问题、影响、PC 端预期与置信度。
3. 最值得先改的 3 项。
4. 无法由当前证据确认的交互待测项；每项包含验证问题、验证动作和通过/失败标准。

全站走查、正式验收或回归任务按以下顺序输出：

1. 结论：通过 / 不通过 / 证据不足。
2. 覆盖范围：页面、交互数、视口与未覆盖项。
3. P0/P1 阻断项。
4. 完整问题表。
5. 建议修复批次及每批 E2E 契约。
6. 回归结果：已修复、仍失败、新增回归。

不得只给“整体不错”“建议优化”等泛化结论。全站走查未点击全部已列入口时，不得声称完成。

可直接复制的独立调用、Agent 委派、全站走查和回归 Prompt 见
