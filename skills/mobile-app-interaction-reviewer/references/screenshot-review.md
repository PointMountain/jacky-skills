# Mobile 截图评审模式

只判断当前手机画面能证明的布局、层级、空间与状态，不推断触控、键盘、手势或网络行为。

## 一、登记画面条件

记录平台、设备或 CSS 视口、方向、系统栏、字体/显示缩放、键盘是否出现、页面与状态。未知项明确写未知；原生截图与 Mobile Web 截图分开标识。

## 二、先扫小屏主矛盾

1. 核心任务和主操作是否在首屏可识别，是否被弹层、输入区、键盘或系统栏遮挡。
2. Header、底栏、悬浮按钮、播放器和输入区各占多少持续空间，剩余内容区是否仍有价值。
3. 同时出现的标签、说明、图标、状态和动作是否超过小屏信息预算；哪些次要内容应渐进披露。
4. 最小文字、最弱对比、最小触控候选和最孤立图标是否影响识别；截图只能把命中区列为待测，不能凭视觉尺寸断言实际触控框。
5. 弹层是否贴边、裁切、出现异常滚动条或压住触发器/主操作；长列表首尾可达仍需运行态验证。
6. 刘海、状态栏、Home indicator、Android 导航栏和圆角区域是否侵入内容。

## 三、平台分离判定

- 看到 PC 的 hover 提示或大浮层被直接压进手机宽度时，问题是容器与信息架构未切换，不建议继续缩字号或压间距。
- 关键说明若只可能通过 hover 出现，直接记录为移动端可发现性缺口；实际点击替代路径未知时列验证任务。
- 不要求 Mobile 复制 PC 的多栏、常驻说明或全部同屏入口；要求业务能力有适合小屏的可发现路径。

## 四、输出

输出一句静态结论、按影响排序的问题、最值得先改的 3 项，以及待实测清单。每个问题包含位置、画面事实、影响、Mobile 预期、严重度和置信度；待实测项写明验证问题、动作和通过/失败标准。
