# 评分标准与等级定义

> 定义 Score Evaluator 各维度的评分细则、等级含义和示例。

## 总体等级

| 等级 | 分数 | 流水线行为 |
|------|------|-----------|
| **A** | 90-100 | ✅ 通过，优秀交付 |
| **B** | 70-89 | ✅ 通过，合格交付 |
| **C** | 50-69 | ❌ 不通过，需修复后重试 |
| **D** | 0-49 | ❌ 不通过，可能需要重新规划 |

**通过线**：加权总分 ≥ 70（即 B 级及以上）

---

## 维度 1：功能正确性 (权重 30%)

### 评分公式

```
功能得分 = (通过的 MUST 数 / 总 MUST 数) × 100
```

### 评分细则

| 分数 | 条件 |
|------|------|
| 90-100 | 所有 MUST 通过，功能完整 |
| 70-89 | ≥80% MUST 通过，核心功能可用 |
| 50-69 | ≥50% MUST 通过，有功能缺失 |
| 0-49 | <50% MUST 通过，核心功能不可用 |

### 示例

```markdown
## MUST 条件 (共 5 条)
- [x] MUST-1: 点击删除按钮弹出确认框 → ✅
- [x] MUST-2: 确认后删除对应 skill → ✅
- [x] MUST-3: 批量选择后可一键删除 → ✅
- [ ] MUST-4: 删除后刷新列表 → ❌ 列表未刷新
- [x] MUST-5: 删除失败显示错误提示 → ✅

功能得分 = 4/5 × 100 = 80
```

## 维度 2：测试覆盖 (权重 25%)

### 评分细则

| 分数 | 条件 |
|------|------|
| 90-100 | 全部测试通过 + 覆盖率 ≥ 80% |
| 70-89 | 全部测试通过 + 覆盖率 60-79% |
| 50-69 | 全部测试通过 + 覆盖率 < 60% |
| 30-49 | 有 ≤2 个测试失败 |
| 0-29 | 有 >2 个测试失败 或 测试无法运行 |

### 评估方法

1. 运行 `pnpm test` 获取测试结果
2. 检查测试文件是否覆盖了关键场景
3. 评估测试质量（不只是数量）：
   - 是否测试了边界情况？
   - 是否测试了错误路径？
   - 测试是否可维护？

### 示例

```markdown
## 测试结果
- 总数: 12
- 通过: 10
- 失败: 2
  - test-batch-delete: 期望 3 个元素，实际 2 个
  - test-error-toast: 超时未出现

测试得分: 40 (有 2 个测试失败)
```

## 维度 3：视觉/UI (权重 20%)

### 免评估条件

当需求不涉及 UI 变更时（如纯后端逻辑、CLI 工具、配置修改），此项 **默认 80 分**。

### 评分细则

| 分数 | 条件 |
|------|------|
| 90-100 | 布局精确、样式一致、响应式完美、交互流畅 |
| 70-89 | 布局正确、样式基本一致、小瑕疵 |
| 50-69 | 布局有问题但不影响使用、样式不一致 |
| 0-49 | 布局错乱、无法正常使用、样式严重偏差 |

### 评估方法

1. **代码审查**：检查 CSS/样式代码的合理性
2. **结构检查**：DOM 结构是否合理
3. **样式一致性**：与项目现有风格是否一致
4. **响应式**：布局是否适配不同尺寸（如项目需要）
5. **交互反馈**：loading 状态、错误状态、空状态是否处理

### 评估清单

```
- [ ] 布局与设计稿/需求一致
- [ ] 字体、颜色、间距符合项目规范
- [ ] 按钮、表单等组件样式统一
- [ ] Loading 状态有展示
- [ ] 错误状态有展示
- [ ] 空状态有展示
- [ ] 响应式布局正常
```

## 维度 4：代码质量 (权重 15%)

### 评分细则

| 分数 | 条件 |
|------|------|
| 90-100 | 可读性优秀、命名清晰、无重复代码、无反模式 |
| 70-89 | 可读性好、命名合理、小瑕疵 |
| 50-69 | 可读性一般、有代码重复、命名不一致 |
| 0-49 | 可读性差、严重反模式、大量重复 |

### 评估维度

#### 可读性
- 函数/变量命名是否清晰
- 代码是否自解释
- 复杂逻辑是否有注释

#### 结构
- 函数职责是否单一
- 组件拆分是否合理
- 是否有过度嵌套

#### 反模式检查
| 反模式 | 扣分 |
|--------|------|
| 未处理的 Promise | -10 |
| 硬编码的魔法数字 | -5 |
| 内联样式滥用 | -5 |
| 过深的回调嵌套 | -10 |
| 未清理的副作用 | -10 |
| 重复的代码块 | -5 |

## 维度 5：计划符合度 (权重 10%)

### 评分细则

| 分数 | 条件 |
|------|------|
| 90-100 | 完全按计划执行，无偏差 |
| 70-89 | 有轻微偏差，记录合理 |
| 50-69 | 有中度偏差，部分改变方案 |
| 0-49 | 严重偏离计划，方案变更大 |

### 评估方法

1. 对比 `PLAN.md` 中的任务列表和 `CHANGES.md` 中的实际执行
2. 检查 `deviations.md`（如有）
3. 评估偏差的合理性

### 偏差评估

| 偏差类型 | 扣分 |
|----------|------|
| 文件路径微调 | -2 |
| 实现方式优化 | -3 |
| 任务合并 | -5 |
| 新增未计划的任务 | -8 |
| 跳过计划中的任务 | -10 |
| 改变整体方案 | -20 |

## 加权计算示例

```markdown
## 评分计算

| 维度 | 原始分 | 权重 | 加权分 |
|------|--------|------|--------|
| 功能正确性 | 80 | 30% | 24.0 |
| 测试覆盖 | 70 | 25% | 17.5 |
| 视觉/UI | 85 | 20% | 17.0 |
| 代码质量 | 75 | 15% | 11.25 |
| 计划符合度 | 90 | 10% | 9.0 |

**总分: 78.75/100 — B 级 — ✅ 通过**
```

## 特殊情况处理

### 缺少测试框架

如果项目没有配置测试框架：
- 测试覆盖维度默认 **50 分**（不鼓励但不过度惩罚）
- Score 报告中标记："项目未配置测试框架，建议补充"

### 纯样式/布局任务

对于纯 UI 调整任务：
- 功能正确性基于"样式是否按预期呈现"
- 测试覆盖可降低要求（视觉测试不易自动化）

### 紧急修复 (Hotfix)

对于紧急修复场景：
- 可以跳过 Plan，直接 Generator → Score
- Plan 符合度维度不适用，权重重新分配：
  - 功能: 40%, 测试: 30%, 代码: 20%, 视觉: 10%
