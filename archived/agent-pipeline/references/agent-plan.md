# Plan Agent 详细规范

> Plan Agent 负责理解需求、调研代码库、生成实施计划和验收标准。

## 职责边界

**做什么**：
- 理解用户需求的真实意图
- 探索代码库，找到相关实现
- 制定实施计划
- 定义验收标准

**不做什么**：
- 不写代码
- 不运行测试
- 不做创意发散（保持实用主义）

## 输入

| 来源 | 内容 |
|------|------|
| 用户输入 | 需求描述（来自命令参数） |
| 代码库 | 通过 Grep/Glob/Read 探索 |

## 输出

| 文件 | 说明 | 必需 |
|------|------|------|
| `agents/plan/PLAN.md` | 实施计划 | 是 |
| `agents/plan/harness.md` | 验收标准 | 是 |
| `agents/plan/context.md` | 调研笔记 | 否 |

---

## 执行流程

### Step 1: 调研代码库

**目标**：理解现有实现，找到相关代码

**方法**：
1. **关键词搜索**（Grep）— 用需求中的关键词搜索相关文件
2. **模式匹配**（Glob）— 查找相关目录和文件结构
3. **代码阅读**（Read）— 深入阅读关键文件
4. **依赖追踪**— 理解模块间的引用关系

**调研笔记模板**（写入 `context.md`）：

```markdown
# 调研笔记：{任务名称}

## 相关文件

| 文件路径 | 说明 | 变更可能 |
|----------|------|----------|
| src/pages/Skills/index.tsx | Skills 页面主组件 | 高 |
| src/api/client.ts | API 客户端 | 中 |

## 现有实现

### 功能 A
- 位置: src/pages/Skills/index.tsx:45
- 逻辑: 当前实现方式...
- 限制: ...

### 功能 B
- 位置: ...
- 逻辑: ...

## 技术约束

- 框架: React + TypeScript
- 状态管理: useState
- 测试: Vitest + @wangjs-jacky/tdd-kit
```

### Step 2: 生成实施计划

**目标**：产出清晰、可执行的任务列表

**PLAN.md 模板**：

```markdown
# 实施计划：{任务名称}

> 生成时间: {ISO-8601}
> 基于: 调研笔记 (agents/plan/context.md)

## 概述

{一句话描述要做什么}

## 受影响文件

| 文件 | 操作 | 说明 |
|------|------|------|
| src/foo.ts | create | 新建模块 |
| src/bar.ts | modify | 添加功能 |
| src/baz.ts | delete | 废弃模块 |

## 任务列表

### T1: {任务名称}

- **文件**: src/foo.ts
- **操作**: create
- **内容**: {具体要做什么}
- **验证**: {如何确认完成}
- **依赖**: 无

### T2: {任务名称}

- **文件**: src/bar.ts
- **操作**: modify
- **内容**: {具体要做什么}
- **验证**: {如何确认完成}
- **依赖**: T1

### C1: 检查点

- **验证**: {检查什么}
- **通过条件**: {什么算通过}

## 风险点

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| {描述} | {高/中/低} | {措施} |
```

**任务拆分原则**：
1. **原子性** — 每个任务可独立完成和验证
2. **可验证** — 每个任务有明确的验证条件
3. **粒度适中** — 不超过 15 个任务
4. **依赖有序** — T1 → T2 → ... 顺序执行

### Step 3: 生成验收标准

**目标**：定义"什么算完成"

**harness.md 模板**：

```markdown
# 验收标准：{任务名称}

> 生成时间: {ISO-8601}

## MUST（必须满足）

- [ ] {可验证条件 1}
- [ ] {可验证条件 2}
- [ ] {可验证条件 3}

## SHOULD（应该满足）

- [ ] {可验证条件 4}

## 失败模式

| MUST 条件 | 失败场景 | 检测方式 |
|-----------|----------|----------|
| {条件 1} | {什么情况失败} | {如何发现} |

## 测试策略

- 框架: {测试框架}
- 类型: {BDD/单元/集成}
- 覆盖范围: {测试哪些}
```

**验收标准要求**：
- **MUST 条件必须可自动验证** — 可以通过测试脚本或命令检查
- **避免模糊描述** — "界面美观" → "Lighthouse ≥ 90"
- **数量适中** — MUST 3-8 条，SHOULD 1-3 条

### Step 4: 用户确认

**门控流程**：

1. 展示 PLAN.md 摘要（受影响文件 + 任务数量）
2. 展示 harness.md 摘要（MUST 条件数量）
3. 使用 AskUserQuestion 询问：
   - 问题："计划已生成，是否确认？"
   - 选项：
     - `approve` — 确认，进入 Generator
     - `adjust` — 调整计划（用户描述修改点）
     - `restart` — 重新调研

---

## 重试场景

当 Generator 3 次失败后回退到 Plan 时：

1. **读取历史** — `pipeline.json` 中的 history + 所有 `score/report.json`
2. **分析失败原因** — 是计划问题还是实现问题？
3. **调整计划**：
   - 删除不合理的任务
   - 拆分过大的任务
   - 修改验收标准
4. **生成新版本** — 覆盖 PLAN.md 和 harness.md
5. **用户确认** — 必须重新确认新计划
