# 评审量规：App UI / 设计

> 用于独立评审一份 App 设计是否可实现、状态完整、可访问且与平台一致。量规只列维度，具体标准随 scope 收敛。

## 事实型 must-pass（先核对）

- **可实现性**：设计是否能用目标技术栈与平台能力落地；是否依赖不存在或成本失控的效果。
- **状态完整**：关键界面是否覆盖空态、加载、错误、无权限、超长内容等状态，而不只是理想态。
- **交互完整性（易漏，必查）**：
  - **无死交互元素**：每一个"看起来可点/可拖/可切"的控件都必须真有行为；纯装饰按钮（如只有样式、无 onPress/handler 的图标按钮）算 fail，要么接上行为要么去掉可点外观。
  - **核心输入路径存在**：产品的主输入必须有真实入口能拿到（如"P 图/生图"类 App 必须能上传/拍摄/选择原图，而不只有内置示例）；主动作到结果的闭环有入口可走通。
  - **空/无资源兜底**：没有内置数据、没有导入内容、无网络/无权限时，用户仍有明确下一步（引导上传、示例、重试），而不是死界面。
- **无障碍基线**：对比度、可点击区域、动态字体、屏幕阅读器语义等是否达到基本可用。
- **平台一致**：导航、手势、系统控件、安全区是否符合目标平台约定，不生搬另一平台范式。
- **移动端渲染细节（易漏，必查）**：
  - **安全区双向**：顶部滚动内容不得穿透到状态栏下（时间/信号压住正文）——要么滚动容器留 `insets.top` 并有导航栏/同色遮罩层挡住下方滚动内容；底部 Tab 栏与悬浮操作要用 `insets.bottom` 抬离系统手势条/Home Indicator，禁止写死高度。
  - **图标质量**：图标必须居中、尺寸一致、风格统一。**禁止用会错位的 unicode 字形**（⤢/☰/✕/⌕/✦ 等在 RN 里基线与字宽不稳，显示偏移或大小不一）充当图标——改用图标字体库（如 `@expo/vector-icons`）或纯矢量/View 绘制。
  - **真机（或等价）渲染核对**：交付 / 发版前至少对关键屏做一次真实渲染截图核对（真机、模拟器或 web 等价渲染），不只凭代码推断——穿透、错位、溢出、对比度这类问题截图能一眼暴露，是本 rubric 的取证方式而非可选步骤。

## 主观质量（事实通过后再评）

- 视觉层级与信息密度是否服务任务，是否有明确的视觉主张。
- 交互反馈、动效是否有意义，而非堆砌。
- 组件与 token 是否可复用、可扩展。

## 判定要点

- 无法实现、关键状态缺失或无障碍不达标，属事实型 fail。
- 只有静态稿、缺少交互/状态说明而无法判断行为，记 `insufficient_evidence`。
- `high_impact_fixes` 优先补齐会阻断实现或验收的缺口，而非美学微调。
