# Skills 设计哲学

我以前设计 Skill，常常从一个看似专业的问题开始：目录应该怎么分，模板应该有哪些字段，是否需要一套完整的协议。这样做很容易获得一种“已经搭好架子”的满足感，但真正运行几次后，我总会发现，文件很整齐，Agent 却仍然不知道该在什么时候看什么、为什么继续、又凭什么相信结果。

后来我把顺序反了过来。我不再先画结构，而是先观察一个人如何把事情做完：他接到什么输入，先检查什么信号，在哪个节点做判断，遇到异常如何回退，最后又用什么事实确认任务真的结束。Skill 的边界不应该来自模板，而应该从这些真实的职责、判断和上下文需求里自然长出来。

## 从人的工作过程开始

一个成熟的工作方法，通常不只是“执行若干步骤”。人在行动之前会观察，在行动之后会验证；如果结果与预期不符，又会回到新的观察。过去我把这些环节拆开写，后来才意识到，观察、行动和验证其实是同一个闭环。

观察让当前处境变得可判断，行动让状态发生变化，验证则回答这个变化是否真的产生了想要的结果。没有观察，行动只是猜测；没有验证，完成只是自我宣布。真正有用的 Skill，应该让 Agent 知道证据在哪里、什么信号足以推动下一步，以及失败时应回到闭环的哪个位置。

这也是我现在理解 Skill 的起点：它不是一组命令的包装，而是一种可重复的判断方式。

## SKILL.md 是地图，不是百科全书

随着经验增加，把所有说明都塞进 `SKILL.md` 是一种很自然的冲动。每次遇到新情况就补一段，久而久之，主文件看似完整，实际使用时却需要先吞下一整本手册。重要规则被细节淹没，Agent 也很难判断当前真正需要读哪一部分。

我更愿意把 `SKILL.md` 看成一张地图和约束入口。它负责说明什么时候进入、哪些边界不能越过、当前处于什么阶段，以及下一步该去哪里寻找细节。具体方法、案例和背景知识可以留在 references、脚本或阶段文件里，按问题出现时再加载。

地图的价值不在于包含所有知识，而在于用最少的信息把人带到正确的位置。

## Workflow 要薄，经验池可以很深

模型已经能够根据目标、代码现场和可用能力判断下一步。Workflow 不应该提前写死技术栈、阶段数量、中间文件和交付位置；它只需要守住目标、权限、验证和停止条件。具体使用 React Native、Expo、Flutter 还是原生，是否需要原型、测试、打包或发布，都应由当前任务和按需加载的能力共同决定。

需要保留的领域知识不必塞进 Workflow。它可以做成独立的经验包 Skill，例如某个成熟项目的架构选择、发布方式、失败复盘和质量门禁。用户要求“参考这个项目的经验”时，Agent 再激活对应 Skill，并沿索引只读取会改变当前决策的少量内容。

因此，“薄”描述的是入口和控制面，不是知识总量。一个 Skill 的本地 Memory 可以保存完整运行资料并增长到很大，只要它默认不进入版本控制，也不会被一次性加载。上下文成本由索引命中的内容决定，而不是由磁盘上保存了多少内容决定。

文件也不应成为同一上下文里的传话筒。上一步结果已经在上下文中时，直接继续推理；只有为了跨会话恢复、长期记忆、真实交付、证据复核或工具文件边界，才值得落盘。

## Workflow 是运行时骨架

Workflow 不应该成为所有任务的默认前置结构。简单任务由 Agent 根据目标、上下文和证据直接判断并执行；只有当任务复杂到需要稳定协作边界时，才在运行时生成一份薄 Workflow，作为当前任务的骨架。

这份骨架固定的是不能在执行中随意漂移的意图：目标、强依赖、用户指定的顺序、授权边界、人工检查门和最终验收。具体动作、能力组合、没有受到硬约束的顺序与并行方式，则保持动态，由 Agent 根据运行中获得的证据调整。这样既不会丢掉关键约束，也不必把开放任务提前压缩成一条僵硬流水线。

如果某类任务需要模板，模板也只保存 Agent 难以自行推断的创作意图。例如“先生成 GPT Image 原型，用户确认后再实现”，其中应固定的是原型先于实现和用户确认这道检查门，而不是把调研、生成、修改、验证的每个动作写成完整 SOP。

## 四种机制，各自解决一个真实问题

我逐渐保留下来的几种机制，并不是为了让 Skill 显得完整，而是因为它们分别回应了运行中的真实摩擦。

复盘解决的是“这次到底发生了什么”。任务结束后，我关心的是目标是否达成、证据是什么、哪些能力实际被使用、哪里发生了降级，以及失败是否已经找到根因。它把一次运行从印象还原为事实，也为后续沉淀设下一道门槛。

有限评分解决的是“怎样提高质量，又不陷入无休止的评审”。复杂工作流可以在阶段交接时独立检查硬事实和主观质量，但每轮只修最重要的一个问题，并限制复评次数。评分的目的不是追求满分或强行收敛，而是在可控成本内发现偏差、推动任务继续。

渐进加载解决的是“知识越来越多后，如何仍然只读取眼前需要的部分”。从主地图进入当前阶段，再进入必要的 reference；从记忆索引进入相关主题，再取少量会改变决策的经验。每深入一层，都应该缩小问题空间，而不是把阅读负担转移到另一个大文件。

可审计事实链解决的是“以后如何知道当时为什么这样做”。我希望留下的是一条可以复核的轨迹：

```text
观察 → 证据 → 决定 → 行动 → 验证 → 错误 → 根因 → 下次规则
```

这条链记录外部可验证的事实和决策依据，让后续的人能够检查、纠正和复用，而不必相信一句笼统的“当时觉得应该如此”。

## 我所说的自进化

自进化很容易被误解成两件事：保存 Agent 的原始思维过程，或者允许 Agent 在一次运行后随意改写自己。我理解的都不是这样。

原始思维过程冗长、偶然，也未必可靠；真正值得保存的是能够被产物、测试、日志或用户确认支撑的事实。一次低分、一次失败甚至一次成功，都不会自动成为长期经验。只有根因得到验证、未来确实可能复现，并且能转化为具体防错动作时，它才值得沉淀。

同样，自进化也需要边界。运行记录只能产生调整候选，不能直接重写稳定规则；候选还要经过验证、查重和回归检查。这样保留下来的不是 Agent 对自己的任意解释，而是能够影响下一次决策、同时又可以追溯和撤销的知识。

## 复杂度应该后来再长出来

并不是每个 Skill 都需要阶段编排、YAML 交接、评分体系和多层记忆。很多简单 Skill 只要写清输入、行动和验收，就已经足够可靠。本机环境事实，以及少量经过验证、只在本机有意义的经验，继续放在 `experience.local.md` 里就很好。它直接、可读，也不会为了架构而制造架构。当内容开始膨胀、需要按 Feature 或 WorkTree 定位，或者单文件已经失去导航能力时，再升级为被忽略的 `local/` 经验池：用短索引进入主题地图，再读取少量原子 Memory，而不是继续扩充一个大文件。

我现在更警惕提前创建空目录、空索引和空协议。复杂度应该由真实内容来支付：当知识多到主文件开始失去导航能力，当任务自然分出稳定阶段，当一组问题反复出现并形成独立的问题簇，再增加 reference、语义地图、结构化契约或记忆层。每一次拆分都应该回答一个已经存在的问题，而不是预演一个也许永远不会出现的未来。

这套想法最终可以归结为一个朴素的判断：先把真实工作看清楚，再决定需要多少结构。好的 Skill 不以文件齐全为目标，而是让 Agent 在恰当的时刻看到少量、可靠、足以改变行动的信息。
