# 运行时薄 Workflow：固定意图，动态路径

> Workflow 是复杂任务在运行时形成的约束骨架，不是每个 Skill 都要预先携带的完整流程。

## 何时不需要 Workflow

目标明确、依赖很少、授权边界清楚，并且可以在一次短闭环中完成的任务，不需要先生成 Workflow。Agent 可以直接理解目标、选择能力、执行动作并验证结果。

例如读取一个本地文件后回答问题，或修改一处文案并运行已有检查，都没有必要为了“流程完整”拆出固定阶段。读取、调研、创作、验证只是任务中可能用到的能力，不是所有任务必须依次经过的通用固定阶段。是否使用它们、以什么顺序使用，应由实际目标和证据决定。

## 何时生成薄骨架

当任务包含多个相互影响的产物、明显的强依赖、跨越授权边界的操作，或必须等待人类判断后才能继续时，Agent 应在运行时生成一份薄 Workflow。它只需让参与者清楚以下问题：

- 最终目标和验收事实是什么；
- 哪些依赖必须先满足；
- 哪些顺序是用户指定的顺序，不能自行交换；
- 哪些行动需要额外授权；
- 哪些节点设有人工检查门；
- 哪些结果足以证明任务完成。

骨架的目的，是防止关键意图在长链路中丢失，而不是预测每个具体动作。

## 固定与动态的边界

运行时 Workflow 应固定难以撤销或不能擅自改变的部分：

- 任务目标与明确的非目标；
- 已确认的强依赖；
- 用户指定的顺序；
- 授权边界与风险限制；
- 人工检查门；
- 验收条件。

其余路径应保持动态：

- 为完成目标采取的具体动作；
- 当下最合适的能力与工具组合；
- 未受硬约束的执行顺序；
- 可以安全并行的工作；
- 新证据出现后的排查、回退和替代方案。

这里的关键不是“阶段越少越好”，而是只固定真正需要稳定的意图。过早固定动态部分，会让 Agent 忽略现场证据，只顾完成预设步骤。

## 模板只表达难推断的意图

模板适合保存某类任务中 AI 难以从普通目标推断出的创作意图，不适合复制一份完整 SOP。

例如一个产品页面任务可以规定：

```text
GPT Image 原型 → 用户确认 → 实现
```

这里值得保存的是两个意图：先用图像原型对齐视觉方向，以及实现前必须通过用户确认。至于是否先调研参考、生成几版原型、用什么能力实现、哪些检查可以并行，都应在运行时按上下文决定。模板越接近逐条操作手册，就越容易把一次成功路径误当成普遍规律。

## 运行中修订

薄 Workflow 不是生成后就冻结。运行中如果出现新的依赖、证据推翻原假设，或用户改变了目标，Agent 应修订骨架，并说明变化影响了哪些约束和后续行动。

修订时应保留稳定边界：没有新的授权，就不能扩大操作范围；没有用户确认，就不能跨过既定人工检查门。动态路径可以随证据变化，固定意图只能由新的事实、明确授权或用户决定来改变。

## 是否落盘

普通任务的 Workflow 只存在于当次运行计划中，不需要写入仓库。把每次短任务都落盘，会制造很快失效的流程文件，也会让稳定设计与临时状态混在一起。

只有长时间运行、需要中断恢复或跨会话交接的任务，才需要持久化当前骨架。此时应写入 gitignored 的私有运行目录，保存恢复所需的目标、约束、检查门、当前状态和证据指针，不把会漂移的运行状态提交为共享设计。

## 反模式

- 为每个任务预建相同的“读取 → 调研 → 创作 → 验证”固定阶段；
- 把能力名称当作业务阶段，要求任务无论是否需要都逐一执行；
- 用模板列出全部命令和操作细节，使 Agent 无法按证据改变路径；
- 把没有强依赖的步骤强制串行，或禁止本可安全进行的并行工作；
- 把人工检查门写成普通提示，尚未确认就继续执行；
- 任务条件已经改变，却为了保持计划整齐而不修订 Workflow；
- 将普通任务的临时计划提交进仓库，长期积累失效状态；
- 仅因为结构化看起来更正式，就为开放任务定义 YAML schema。
