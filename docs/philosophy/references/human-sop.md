# 从真实人类 SOP 反推 Skill

> 设计 Skill 前先研究人真实怎么完成任务。本文件解决“阶段和能力从哪里来”，不负责规定具体目录。

## 核心原则

Skill 是对真实工作方法的固化，不是对理想组件图的实现。抽象必须能追溯到实际观察：谁在什么情境下，看见什么信号，做出什么判断，采取什么行动，最后如何确认结果。

## 调研顺序

1. **选真实案例**：至少找一个成功案例和一个失败或返工案例。
2. **跟随完整过程**：从输入出现到结果验收，不只看中间的执行动作。
3. **标记观察点**：操作者在每一步看哪些页面、文件、状态、日志或视觉结果。
4. **标记判断点**：哪些证据导致继续、回退、换工具或找人确认。
5. **标记行动与产物**：动作产生什么可检查的中间工件。
6. **标记验收方式**：什么事实证明完成，什么只是“看起来差不多”。
7. **标记异常路径**：工具不可用、结果不可信或前置条件缺失时，人怎么处理。
8. **最后才拆 Skill**：只有职责、输入输出或上下文需求确实不同，才拆为独立 Skill。

## SOP 卡

每个阶段至少回答以下问题：

```markdown
### <阶段名称>

- 触发：什么事实说明应该进入这一阶段？
- 输入：上一步交付了什么？
- 观察：必须看哪些信号？
- 证据：这些信号从哪里获取，如何复核？
- 判断：什么条件决定继续、返工、降级或停止？
- 行动：执行哪些动作，允许多大自由度？
- 产物：输出什么可检查的工件？
- 验收：哪些是 must-pass，哪些属于主观质量？
- 异常：外部能力不可用时怎么回退？
- 记忆候选：哪些错误可能值得跨次保留？
```

## 从 SOP 决定边界

满足下列任一条件时，才值得拆出独立 Skill：

- 有独立触发条件和清晰结束条件；
- 产物能被下一阶段单独消费和验证；
- 需要与主流程显著不同的工具或上下文；
- 会被多个工作流复用；
- 现有主 Skill 因细节膨胀而失去地图作用。

仅仅拥有一个好听的名词，不构成拆分理由。`background`、`feature` 等能力应在真实 SOP 中形成独立职责后再拆。

## 观察优先于自报状态

外部 Skill、模型或工具说“已经完成”只是一个信号，不是证据。设计 SOP 时优先保留人原本会做的复核动作，例如：

- 打开真实产物，而不是只读成功消息；
- 对照输入来源，而不是相信生成摘要；
- 运行测试或探针，而不是推测环境可用；
- 检查最终用户看到的界面，而不是只检查文件存在。

## 反模式

- 先画完整架构，再寻找现实流程为它背书；
- 把所有可能的角色都预建成 Skill；
- 只编码正常路径，不记录观察、验收和回退；
- 把工具名称当能力边界；
- 用抽象评分代替真实验收证据。
