# Harness Benchmark — Skill 质量基准评估 设计文档

> 日期：2026-03-28
> 状态：待审核（第三轮）

## 一、背景与动机

### 问题

当前 task-harness skill 只做一件事：把验收标准转成可执行测试。但"驾驭 AI 开发"远不止测试用例 — 它是一个完整的纪律体系：

1. 决策是否持久化到了文件，还是丢在聊天上下文中？
2. 开发前是否写清了边界、步骤和风险？
3. 进度是否可通过文件追踪，而非口头同步？
4. 是否强制 TDD 流程，而不是"先写代码再补测试"？

**核心痛点**：缺少一个工具来评估一个 Skill 是否具备"驾驭 AI"的能力。

### 理想的 Harness 流程（参考模型）

一个被完整驾驭的 AI 开发流程应该是这样的：

```
接收任务 → 明确模块/主题/边界/目标（不写代码）
    ↓
检索已有实现（不自由发挥，复用现有代码）
    ↓
创建/更新 Spec（写入文件，功能可追踪）
    ↓
汇总蓝图（目标、边界、依赖、受影响文件、任务清单、风险点）
    ↓
┌─────────────────────────────────────┐
│  门禁：上述全部满足才允许进入实现    │
│  否则 → 回到明确阶段继续澄清        │
└─────────────────────────────────────┘
    ↓
按任务清单逐项实施（每项完成后回写状态）
    ↓
上下文溢出？→ 保存进度 → 新会话从断点恢复
```

**核心原则**：让 AI 稳定地以可控方式进行开发，而不是盲目开发。

### 目标

创建 `harness-benchmark` skill，用于评估 **其他 Skill（SKILL.md）** 的质量 — 衡量它们是否能让 AI 以可控、可回溯、TDD 驱动的方式工作。

## 二、Harness 参考模型 — 7 阶段

理想的 Harness 流程包含 7 个阶段，每个阶段有明确的输入、输出和门禁：

```
阶段 1: CLARIFY（明确）
  输入：用户任务描述
  输出：模块、主题、边界、目标 四要素
  门禁：四要素全部明确
  关键约束：此阶段禁止写任何代码

阶段 2: SEARCH（检索）
  输入：四要素
  输出：当前模块中已有的相似实现列表
  关键约束：不自由发挥，优先复用

阶段 3: SPEC（规格化）
  输入：四要素 + 已有实现
  输出：Spec 文件（写入 .harness/specs/），功能可追踪
  门禁：Spec 经过用户确认

阶段 4: BLUEPRINT（蓝图汇总）
  输入：已确认的 Spec
  输出：汇总文件，包含：
    - 目标与边界
    - 依赖关系
    - 受影响文件列表
    - 任务清单（可逐项勾选）
    - 风险与回归点
  门禁：汇总文件经用户确认，所有项无遗漏

阶段 5: TEST（测试先行）
  输入：蓝图汇总 + 任务清单
  输出：覆盖所有 MUST 条件的测试用例（全部 Red）
  门禁：所有测试编写完成且运行失败（Red 状态）

阶段 6: IMPLEMENT（按清单实施）
  输入：蓝图 + 失败测试
  输出：通过测试的实现代码（Green → Refactor）
  关键行为：
    - 按任务清单逐项实施
    - 每完成一项 → 回写状态到文件
    - 每完成一项 → 运行测试验证
  门禁：所有测试通过（Green）

阶段 7: VERIFY（验证与收尾）
  输入：全部通过的测试
  输出：
    - 最终状态更新
    - 回归测试报告
    - 受影响文件清单确认
  门禁：回归测试全部通过
```

### 中断恢复机制

任何阶段如果遇到上下文溢出，必须支持：
1. 当前进度已写入文件（不是聊天）
2. 新会话可从 `.harness/state.json` 读取当前阶段和进度
3. 从断点继续，而非从头开始

## 三、5 个评估维度

基于上述 7 阶段模型，提炼出 5 个评估维度：

### D1: 任务明确性（Task Clarity）— 对应阶段 1-2

**核心问题**：Skill 是否要求在写代码之前先明确四要素（模块、主题、边界、目标）并检索已有实现？

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否禁止在明确阶段写代码 | 0-2 | 明确规定"不写代码"或等价约束 |
| 是否要求明确模块和主题 | 0-2 | 任务归属到具体模块 |
| 是否要求明确边界和目标 | 0-2 | 边界 = 改动范围，目标 = 完成定义 |
| 是否要求检索已有实现 | 0-2 | 复用优先，不自由发挥 |
| 是否支持需求反复澄清 | 0-2 | 用户可多轮确认 |

### D2: 文件化持久化（File Persistence）— 对应阶段 3-4

**核心问题**：关键决策和产出是否写入文件？

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否要求 Spec 写入文件 | 0-2 | 规格化产出是文件而非聊天内容 |
| 是否要求蓝图汇总写入文件 | 0-2 | 目标/边界/依赖/任务/风险 全部落文件 |
| 决策是否可回溯 | 0-2 | 历史决策有文件记录 |
| 上下文是否可跨会话迁移 | 0-2 | 新会话能从文件恢复完整上下文 |
| 产出是否有版本追踪 | 0-2 | 文件变更可追溯 |

### D3: 状态系统（State System）— 贯穿全流程

**核心问题**：是否有门禁系统控制阶段流转，进度是否可通过文件追踪？

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否定义了明确的阶段 | 0-2 | 有清晰的阶段划分和名称 |
| 阶段间是否有门禁 | 0-2 | 进入下一阶段需要满足条件 |
| 是否有"蓝图不齐不进入实现"的硬门禁 | 0-2 | 核心安全门：不满足条件不允许写代码 |
| 进度是否实时回写到文件 | 0-2 | 每完成一项 → 状态文件更新 |
| 是否支持中断恢复 | 0-2 | 上下文溢出后可从断点继续 |

### D4: TDD 流程纪律（TDD Discipline）— 对应阶段 5-6

**核心问题**：Skill 是否强制"先写测试再实现"？

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否要求先写失败测试（Red） | 0-3 | 明确要求在实现前编写测试用例 |
| 是否要求实现使测试通过（Green） | 0-3 | 实现阶段以"让测试通过"为目标 |
| 是否要求重构（Refactor） | 0-2 | 通过测试后进行重构优化 |
| 测试是否作为验收标准 | 0-2 | 测试用例 = "完成"的定义 |

### D5: 边界与风险前置（Boundary & Risk Upfront）— 对应阶段 4

**核心问题**：蓝图汇总中是否包含完整的边界、风险和回归信息？

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否要求列出受影响文件 | 0-2 | 明确哪些文件/模块会被修改 |
| 是否要求识别依赖关系 | 0-2 | 列出功能间的依赖 |
| 是否要求列出风险与回归点 | 0-2 | 最可能出错的地方和回归测试策略 |
| 是否要求定义失败模式 | 0-2 | 出错时如何回退 |
| 是否要求定义执行顺序 | 0-2 | 任务清单有先后依赖关系 |

### D6: 复杂度适配性（Complexity Adaptability）— 贯穿全流程

**核心问题**：Skill 的流程复杂度是否能根据任务复杂度自适应？简单任务不会因为流程过重而浪费人类注意力？

**评分哲学**：满分 50 不是目标。一个好的 Skill 是在"纪律"和"效率"之间找到平衡 — 简单任务轻流程，复杂任务重流程。**对简单任务强制走完整 7 阶段和没有纪律一样糟糕**，因为它浪费了人类注意力这个最稀缺的资源。

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否提供多档流程模式（如 quick/standard/yolo） | 0-2 | 不同复杂度的任务走不同深度的流程 |
| 是否有任务复杂度判断机制 | 0-2 | 能自动或手动判断任务是简单/中等/复杂 |
| 简单任务是否可以跳过非必要阶段 | 0-2 | 不强制所有任务走完整流程 |
| 核心门禁是否在所有模式下都保留 | 0-2 | quick 可以跳 BRAINSTORM，但不能跳 VERIFY |
| 流程开销是否与任务价值匹配 | 0-2 | 一句话能解决的需求不应该产生 7 个文件 |

**评分标准**：
- 0-3：只有一种模式，所有任务都走完整流程（或完全没有流程）
- 4-6：有多档模式但选择不够智能，或跳过逻辑不够灵活
- 7-10：流程复杂度自适应，简单任务轻量通过，复杂任务严格门控，核心安全门始终保留

### D6: 复杂度适配性（Complexity Adaptability）

**核心问题**：Skill 是否能根据任务复杂度自动调节流程？简单任务是否可以轻量化，而不是强制走完所有阶段？

**核心理念**：

> 流程的复杂度应该和任务的复杂度匹配。一句话能改完的 bug，不需要走 7 个阶段。满分不存在 — 好的 Skill 是在"纪律"和"效率"之间找到平衡。

| 检查项 | 分值 | 说明 |
|--------|------|------|
| 是否提供快速模式（跳过非必要阶段） | 0-3 | 如 `quick` / `yolo` 模式，简单任务可跳过 BRAINSTORM |
| 阶段是否可按需跳过（而非全有或全无） | 0-2 | 不同阶段可独立跳过，而非只提供"全流程"和"跳过全部"两个极端 |
| 门禁是否可简化（简单任务降低确认次数） | 0-2 | 简单任务不需要每步确认 |
| 是否有任务复杂度判断机制 | 0-3 | Skill 是否引导 AI 或用户判断"这个任务需要几步" |

**评分标准**：
- 0-3：只有全流程，没有快速通道。改个颜色也要走 7 个阶段。
- 4-6：有快速模式但只有全有或全无（要么全走要么全跳）
- 7-10：细粒度适配 — 可按阶段跳过、按任务复杂度自动建议流程级别

**关键洞察**：
- 强制所有任务走完整流程 = 减分项（浪费人类注意力）
- 没有任何快速通道 = 扣分
- 能根据任务复杂度推荐合适的流程级别 = 高分

## 四、评分体系

### 评分哲学

**满分不是目标，平衡才是。**

这个评估体系的设计意图不是让每个 Skill 都拿到 50 分。实际上：

- 一个 50 分的 Skill 可能意味着流程过重，不适合日常简单任务
- 一个 35-40 分的 Skill，如果 D6（复杂度适配性）得分高，可能是最实用的
- 永远在"纪律"和"效率"之间做取舍

**评估不是为了追求满分，而是为了发现短板和过重之处。**

### 维度评分

每个维度 0-10 分，6 个维度总分 0-60。

### 等级划分

### 维度评分

每个维度 0-10 分，6 个维度总分 0-60。

### 评分哲学

**满分 60 不等于"最好"**。一个真正好的 Skill 会在 6 个维度间找到平衡：

```
D6 (复杂度适配) 是调节器：
- D6 高分 + 其他维度中等 = 优秀的轻量级 Skill
- D6 高分 + 其他维度高分 = 优秀的重量级 Skill
- D6 低分 + 其他维度高分 = 过度工程化的 Skill（减分）
- D6 低分 + 其他维度低分 = 无纪律的 Skill
```

**不存在"完美 Skill"** — 完美意味着所有检查项都通过，但这意味着最简单的任务也要走完整流水线。好的 Skill 是知道什么时候该简化的。

### 等级划分

| 总分 | 等级 | 标签 | 含义 |
|------|------|------|------|
| 48-60 | S | Balanced Harness | 纪律与效率兼顾，流程自适应，AI 可控且高效 |
| 36-47 | A | Well Harnessed | 大部分到位，少量改进即可 |
| 24-35 | B | Partially Harnessed | 有基本控制，但关键门禁或适配能力缺失 |
| 12-23 | C | Loosely Harnessed | 约束不足或流程过重，AI 容易失控或效率低 |
| 0-11 | D | Unharnessed | 无纪律框架，或流程过重导致无法使用 |

### 维度与阶段映射

```
D1: 任务明确性     ──→ 阶段 1 (CLARIFY) + 阶段 2 (SEARCH)
D2: 文件化持久化   ──→ 阶段 3 (SPEC) + 阶段 4 (BLUEPRINT)
D3: 状态系统       ──→ 贯穿全流程（门禁 + 回写 + 恢复）
D4: TDD 流程纪律   ──→ 阶段 5 (TEST) + 阶段 6 (IMPLEMENT)
D5: 边界风险前置   ──→ 阶段 4 (BLUEPRINT) 的产出质量
D6: 复杂度适配性   ──→ 调节器：简单任务轻流程，复杂任务重流程
```

## 五、工作流程

### 阶段 1：扫描（Scan）

输入：一个 SKILL.md 文件路径

操作：
1. 读取 SKILL.md 全文
2. 检查 references/ 目录下的参考文件
3. 识别 skill 的结构特征：
   - 是否有 `gsd:workflow` / `gsd:phase` 定义
   - 是否有 `<process>` / `<step>` 标签
   - 是否有明确的 `<philosophy>` 或 `<principle>` 部分
   - 是否定义了输出文件路径
   - 是否有状态管理相关内容
4. 检查 `.harness/` 目录结构（如果存在）

### 阶段 2：审查（Checklist Review）

按 5 个维度逐项检查，每项给出 ✅ Pass / ⚠️ Partial / ❌ Fail：

```
D1: 任务明确性
  [✅] 禁止在明确阶段写代码
  [✅] 要求明确模块和主题
  [⚠️] 要求明确边界和目标（隐含但未显式要求）
  [❌] 要求检索已有实现
  [✅] 支持需求反复澄清
  → 6/10

D2: 文件化持久化
  [❌] 要求 Spec 写入文件
  [❌] 要求蓝图汇总写入文件
  [❌] 决策可回溯
  [❌] 上下文可跨会话迁移
  [❌] 产出有版本追踪
  → 0/10
...
```

### 阶段 3：评分（Scoring）

汇总各维度分数，计算总分和等级。

### 阶段 4：改进计划（Improvement Plan）

输出按优先级排序的具体改进建议，每条包含：
- 对应维度和检查项
- 当前状态和目标状态
- 具体的 SKILL.md 修改建议（可直接复制的内容片段）
- 预计提升分数

```markdown
### P0: 添加文件化要求（预计 +8 分）

当前状态：所有产出只在聊天中，关了就没了。
目标状态：Spec 和蓝图写入 .harness/ 目录。

建议在 SKILL.md 的 <process> 中添加：

  <step name="spec" priority="critical">
  **目标**：将需求规格化并写入文件
  **输出**：.harness/specs/<feature-name>.md
  **门禁**：用户确认 Spec 后才能进入下一阶段
  </step>
```

### 阶段 5：报告持久化（Save Report）

所有结果写入文件：

```
.harness/benchmark/<skill-name>/
├── report.md           # 完整评分报告
├── checklist.md        # 审查清单（逐项 pass/fail）
└── improvement.md      # 改进计划（含可直接使用的代码片段）
```

## 八、参考标准

### S 级 Skill 特征（Fully Harnessed）

```xml
<gsd:workflow>
  <gsd:phase id="1" name="clarify">
    明确模块、主题、边界、目标。此阶段禁止写任何代码。
  </gsd:phase>
  <gsd:phase id="2" name="search">
    检索当前模块已有实现，优先复用。
  </gsd:phase>
  <gsd:phase id="3" name="spec">
    将需求规格化，写入 .harness/specs/<feature>.md。用户确认后进入下一阶段。
  </gsd:phase>
  <gsd:phase id="4" name="blueprint">
    汇总蓝图：目标、边界、依赖、受影响文件、任务清单、风险点。
    写入 .harness/blueprints/<feature>.md。用户确认后进入测试。
  </gsd:phase>
  <gsd:phase id="5" name="test">
    为每个 MUST 条件编写失败测试。所有测试运行失败（Red）后进入实现。
  </gsd:phase>
  <gsd:phase id="6" name="implement">
    按任务清单逐项实施。每完成一项 → 回写状态 → 运行测试验证。
  </gsd:phase>
  <gsd:phase id="7" name="verify">
    全量回归测试。更新最终状态。确认受影响文件清单。
  </gsd:phase>
</gsd:workflow>

<!-- 中断恢复 -->
<recovery>
  状态持久化到 .harness/state.json。
  新会话从 state.json 读取当前阶段和进度，从断点继续。
</recovery>
```

### D 级 Skill 反模式

1. 没有阶段划分，直接"实现 X 功能"
2. 测试是可选的或事后补充
3. 所有信息只在聊天中传递
4. 没有门禁，一口气做完
5. 不定义边界，AI 自由发挥
6. 不检索已有实现，重复造轮子
7. 中断后无法恢复，从头开始
