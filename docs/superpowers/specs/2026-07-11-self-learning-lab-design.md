# Self Learning Lab：设计

> 把现有的“教学视频生成 HyperFrames Demo”实验，重组为一套由 AI 从外部素材自主学习、扩展调研并创造可验证产物的实验性能力。

## 背景

现有 `tutorial-to-hyperframes-demo` 已经证明模型可以从教学视频中理解方法、观察动效、生成 HyperFrames Demo 并观看修正。它的实际生成效果可用，但当前名称和封装把能力限制在“教学视频 + HyperFrames + 视频 Demo”，并把摄取、转录、学习、创作、评分、恢复和审计等职责固化为一条庞大的固定流程。

用户真正想验证的是更一般的能力：AI 从视频、文章或链接中识别技术知识与方法，围绕知识点继续调研，再把自己的理解转化成 Demo、教程、笔记或其他可验证产物。这里的“学习”不表示模型训练、微调、修改权重，也不要求自动生成新的 Agent Skill。

## 目标

- 建立 `labs/self-learning/` 实验域，统一承载 AI 自主学习与创作实验。
- 提供一个轻量总入口 `self-learning`，由 AI 按任务现场决定执行路径和能力组合。
- 把现有 Skill 移入实验域并重命名为 `self-learning-hyperframes`，保留当前可用行为。
- 支持用户提供视频、文章或链接，也允许 AI 从主题出发寻找学习素材。
- 视频平台第一阶段限定为 YouTube、B 站和抖音；普通网页文章继续作为通用来源。
- 允许输出 Demo、教程、笔记及任务要求的其他可验证产物，不预设唯一交付格式。
- 把“运行时薄 Workflow”补充为仓库级 Skills 设计哲学。

## 非目标

- 不实现新的平台下载器、搜索引擎、浏览器、ASR 或渲染器。
- 不把三个视频平台分别拆成新的空 Skill。
- 不在本轮把现有七千余行实现全面重写或拆成固定阶段子 Skill。
- 不为 `self-learning` 创建固定 `workflow.yaml`、工作流引擎或预置的完整 SOP。
- 不修改 `web-flow`；它只作为渐进加载和外部能力组合的现有参考。
- 不把 Self Learning 解释为模型训练、自我修改或 Agent Skill 自动生成。

## 命名与目录

正式名称统一使用 kebab-case：

```text
labs/self-learning/
├── README.md
├── self-learning/
│   └── SKILL.md
└── self-learning-hyperframes/
    ├── SKILL.md
    ├── agents/
    ├── references/
    ├── scripts/
    └── tests/
```

- `self-learning` 是用户入口和动态调度地图。
- `self-learning-hyperframes` 是当前已经存在的完整实验链路，不代表 Self Learning 的通用架构。
- 以后只有真实任务形成稳定、可复用的职责边界时，才增加新的子 Skill；不预建空目录。

## 核心哲学：固定意图，动态路径

Workflow 不是预先穷举的执行剧本，而是任务运行时生成、允许修订的行动骨架。

固定部分来自用户意图或场景模板，包括：

- 必须使用的能力，必要时可以指定具体工具，例如 GPT Image；
- 必须先出现的中间产物；
- 必须停下来让用户查看或确认的决策门；
- 不可逆操作的授权边界；
- 确实存在的先后依赖和最终验收条件。

动态部分由 AI 决定，包括：

- 是否需要显式 Workflow；
- 具体阶段、步骤数量和执行顺序；
- 搜索、下载、转录、浏览、创作和验证能力的选择；
- 哪些产物对当前知识最合适；
- 新证据出现后是否调整行动骨架。

简单、确定性的任务允许 AI 直接执行，不强制制造 Workflow 文件。复杂、长时间、无人值守或有明确创作顺序的任务，应先生成一份薄 Workflow。模板只注入 AI 难以自行推断的意图、依赖和决策门，不能接管全部执行细节。

本文出现的“摄取、理解、调研、创作、验证”只是可能被调用的能力集合，不是所有任务必须依次经过的阶段状态机。AI 可以按证据跳过、合并、重排、并行或增加动作；只有用户意图、强依赖、人工检查门、授权边界和真实依赖关系不可擅自删除。

## 运行模型

### 输入

`self-learning` 接收以下任一种入口：

- 用户提供的本地视频或音频；
- YouTube、B 站或抖音链接；
- 普通网页文章或用户提供的文案；
- 一个主题，由 AI 在上述平台和网页中寻找适合的学习素材。

当用户只给主题时，AI 仍需建立可追溯的来源集合，不能把模型记忆伪装成本轮调研事实。

### 动态编排

1. 判断用户真正想学什么、希望得到哪些产物，以及是否存在强依赖或人工检查门。
2. 判断任务是否简单到可以直接执行；只有需要协调、恢复或显式约束时才生成薄 Workflow。
3. 从当前 Skill catalog 和工具面按需寻找搜索、网页访问、平台摄取、转录、调研、素材、创作和验证能力。
4. 在能力首次使用时验证其真实可用性；不因目录存在或工具自报成功而视为可用。
5. 自主完成学习、补充调研和产物创作；不要求所有任务经过同一组阶段。
6. 新证据改变原计划时允许修改 Workflow，并记录改变依据；只有用户预设的检查门、范围实质变化或外部写入授权缺失时才暂停。
7. 以真实产物和可复核证据判断完成，不以“已生成”消息代替验收。

### Workflow 的保存

- 简单任务可以不创建 Workflow 工件。
- 普通复杂任务优先使用 Agent 当前任务计划，不在仓库中制造固定协议。
- 只有无人值守、耗时较长或需要断点恢复时，才把本轮薄 Workflow 和状态写入目标工程的 gitignored 私有运行目录。
- Workflow 属于本轮运行状态，不是稳定产品配置；稳定模板只保存意图约束、强依赖、决策门和验收条件。

需要显式表达薄骨架时，只要求说明本轮的 `objective`、`constraints`、`required_capabilities`、`checkpoints` 和 `acceptance`。这些是语义边界，不要求建立固定 YAML schema，也不预先定义通用 `steps`、阶段枚举或所有可能分支。AI 在本轮选择的具体动作仍属于可修改的运行状态。

### 产物

产物由知识性质和用户目标决定，可以包含：

- 可运行、可交互或可观看的 Demo；
- 面向读者的教程；
- 带来源和理解脉络的学习笔记；
- 支撑结论的代码、截图、渲染结果、测试或其他验证材料。

不是每个任务都必须同时生成 Demo、教程和笔记。AI 应选择能证明自己真正理解了知识、同时符合用户目的的最小产物集合。

## 能力组合边界

总入口按“需要什么能力”选择现有 Skill，而不是复制其实现或永久绑定单一提供者。

- 平台发现、网页访问和搜索可调用 OpenCLI、Web Access 或当前可用的浏览器能力。
- 平台下载与内容提取调用现有视频能力。
- 音视频转录调用现有字幕或 ASR 能力。
- Demo 创作可以调用 HyperFrames、Motion、网页实现或未来出现的其他能力。
- 教程与笔记使用当前可用的文档和知识沉淀能力。

用户或模板明确指定具体工具时，该指定高于自动候选选择。例如“必须先用 GPT Image 生成原型，并在用户确认后才能实现”应成为硬依赖和人工检查门，而不是被替换成普通设计步骤。

## 现有 HyperFrames 实验的迁移

本轮采用保护性迁移：

- 将 `skills/tutorial-to-hyperframes-demo/` 移到 `labs/self-learning/self-learning-hyperframes/`。
- 把 frontmatter、标题、默认提示、README 索引、活动路径引用和测试期望改为 `self-learning-hyperframes`。
- 保留现有脚本、契约、评分和测试行为，不借重命名全面重构内部流程。
- 本次是一次明确的 breaking rename：不保留可调用的 `tutorial-to-hyperframes-demo` 别名；旧的全局链接和安装记录必须移除，再显式链接并安装 `self-learning` 与 `self-learning-hyperframes`。
- 旧名称若作为已有运行状态的持久标记存在，只能以明确标注的兼容分支保留，并增加迁移测试；不能继续作为公开主名称或触发入口。
- 原实现设计与计划文档属于历史记录，可以保留历史文件名和原始叙述；任何被当前文档或命令使用的活动路径必须更新。
- 迁移清单必须覆盖目录、frontmatter `name`、标题、`agents/openai.yaml` 默认提示、README、当前测试、脚本内持久标记、全仓活动引用、全局链接和安装记录。
- `labs/` 不进入仓库一键安装扫描，且本轮不修改 `install.sh` 扩大扫描范围。需要本机继续调用时，使用 `j-skills` 显式链接、安装两个新名称并执行发现性 smoke test。

## 错误与降级

- 来源无法访问：尝试当前可用的同类能力或请用户提供本地素材，不静默用模型记忆代替。
- 平台能力缺失：保留来源和失败证据，选择合法 fallback；所有合理候选都失败时明确阻断。
- 学到的知识不足以创作 Demo：允许只交付教程或笔记，但必须说明缺失的验证环节，不能伪装成完整掌握。
- 指定的强依赖不可用：不得擅自替换；应在对应决策门报告阻断或请求用户调整约束。
- 执行中发现 Workflow 不合适：允许修改动态路径，但不能删除用户预设的硬依赖、授权边界或人工检查门。
- 产物不可运行、不可观看或来源不可追溯：视为未完成，继续修正或明确保留 residual。

## 文档变化

在 `docs/philosophy/README.md` 增加“运行时薄 Workflow”核心章节，并新增一篇聚焦以下内容的 reference：

- 简单任务直接执行与复杂任务生成骨架的判断；
- 固定意图、动态路径的边界；
- 模板如何表达强依赖、顺序和人工检查门；
- Workflow 如何基于证据修订；
- 为什么不把 YAML 变成工作流引擎。

入口文档必须链接到新 reference，并与“复杂度应该后来再长出来”“外部能力按槽位探测”的既有原则保持一致。

## 验收

- `labs/self-learning/README.md` 能让读者区分 Self Learning 与模型训练。
- `self-learning/SKILL.md` 只保存触发边界、动态决策规则、硬约束和能力路由，不固化统一阶段表。
- 原目录不再作为活动 Skill 存在，新目录与 frontmatter 名称一致。
- `self-learning-hyperframes` 的原有自有测试在新路径全部通过。
- 所有活动文档、提示、README 与测试不再把旧名称作为当前入口。
- 旧持久标记若保留，仅用于兼容且有测试覆盖。
- 哲学文档明确写出“固定意图，动态路径”和运行时薄 Workflow。
- `README.md` 的 Labs 区域列出 `self-learning`，独立 Skills 区域移除旧名称。
- 新实验不被 `install.sh` 当作正式 Skill 批量安装；旧名称从本机全局链接和安装记录中移除，两个新 Skill 可通过显式链接、安装和调用 smoke test 被发现。
- 使用一个已有成功素材或原有测试夹具，至少完成一次迁移后 `init / validate / HyperFrames check-render` 路径 smoke test，证明改名和相对路径没有破坏现有链路；不要求本轮重新创作一个新 Demo。
- 仓库全量单元测试、共享内容审计、`install.sh` 语法检查与 Plugin 严格校验通过；同时单独运行 labs 下迁移后的全部自有测试。

## 实施边界

本轮只建立实验域、总入口、保护性迁移和哲学文档。是否把现有 HyperFrames 流程拆分、是否增加平台适配 Skill、是否沉淀视觉优先模板，都应由后续真实 Self Learning 任务提供证据后再决定。
