# 滴答清单自动化任务池设计

> 将滴答清单作为「任务池」，本地推送任务、远程自动执行的异步工作架构

## 术语约定

| 术语 | 含义 |
|------|------|
| **任务池** | 滴答清单中专门用于存放待自动执行任务的清单项目 |
| **任务池 projectId** | 首次运行时自动检测或创建，统一存储在共享配置中 |

> **注意**：任务池清单无需用户手动创建。`tt-defer` 首次运行时自动检测名为「任务池」的清单，不存在则通过 `tt` CLI 创建。

## 背景

本地 MacBook Air（M2）性能有限，无法同时承载大量任务。需要一个机制将不急于执行的任务推送到任务池中，由远程服务器在合适的时间自动完成。

滴答清单天然适合作为任务池 — 已有完善的 tt skill 和 tt-cli 基础设施，任务天然带有结构化信息。

## 核心架构

```
┌─────────────────────┐          ┌──────────────────────┐
│   本地 MacBook Air   │          │    远程服务器（可配置）  │
│                     │          │                      │
│  ┌───────────────┐  │          │  ┌────────────────┐  │
│  │  tt-defer     │──┼── 推 ──→ │  │  滴答清单       │  │
│  │  (推送端)      │  │          │  │  「任务池」      │  │
│  └───────────────┘  │          │  └───────┬────────┘  │
│                     │          │          │ 读         │
│  使用场景：          │          │  ┌───────▼────────┐  │
│  - 生成 plan 后推    │          │  │  tt-worker     │  │
│  - 生成 spec 后推    │          │  │  (执行端)       │  │
│  - 文章/调研推       │          │  └────────────────┘  │
│  - 任何延迟任务      │          │                      │
└─────────────────────┘          └──────────────────────┘
```

## 核心约定

### 专用清单

滴答清单中有一个专门的清单项目作为「任务池」。所有自动化任务只在此清单中读写：

- **tt-defer** 只往这个清单推送任务
- **tt-worker** 只从这个清单读取任务

不会读写其他清单（如 Inbox、蓝、红等）。清单名称默认为「任务池」，首次运行自动创建。

### 任务类型使用 TickTick Tag

任务类型不写在 content 里，而是使用滴答清单原生的 **tag（标签）** 功能：

| Tag | 含义 | 执行方式 |
|-----|------|---------|
| `plan-exec` | Plan 执行 | 按 plan 逐步执行代码 |
| `spec-dev` | Spec 开发 | 根据 spec 开发新功能 |
| `research` | 调研分析 | 搜索资料、分析、输出报告 |
| `article` | 文章阅读 | 阅读并提炼要点，摘要写入 Obsidian |
| `code-task` | 代码任务 | 通用代码任务 |

tt-cli 已原生支持 `--tag` 参数：`tt task-add "标题" --tag plan-exec`

**Tag 的优势**：
- 在滴答清单 UI 中直观可见、可按 tag 筛选
- content 保持干净，只保留执行信息
- tt-worker 可按 tag 决定执行策略
- 用户可在滴答清单中手动修改 tag 来调整执行方式

## 任务格式

推到滴答清单的任务需自带完整上下文，因为远程执行时没有原始对话。

### 滴答清单任务结构

**标题**：简短描述做什么（≤15 字）

**Tag**：任务类型标签（见上方 tag 表）

**内容（Markdown）**：

```markdown
## 原始背景
（必填）为什么需要这个任务？用户原始需求是什么？

## 前置决策
（可选）已经考虑过/排除的方案、重要的决策依据

## 执行环境
仓库路径：/path/to/repo
分支：feature-xxx（可选）
相关文件：path/to/file1, path/to/file2（如有具体文件，列出完整路径）

## 执行计划
（完整的 plan 或 spec 内容直接贴在这里）

## 预期产出
描述期望的产出物

## 备注
额外说明
```

### Tag 自动推断规则

`tt-defer` 根据以下规则自动推断 tag，用户也可手动指定覆盖：

| 上下文特征 | 推断 Tag | 置信度 |
|-----------|---------|--------|
| 当前会话生成了 plan 文件（含 Step/Task 结构） | `plan-exec` | 高 |
| 当前会话生成了 spec/设计文档（含需求/API 设计） | `spec-dev` | 高 |
| 用户提供 URL 或文章链接 | `article` | 高 |
| 用户描述涉及"调研"、"研究"、"分析" | `research` | 中 |
| 以上均不匹配 | `code-task` | 默认回退 |
| 用户手动指定 tag | 用户指定 | 最高（覆盖推断） |

## tt-defer skill（推送端）

**位置**：`plugins/ticktick-manager/tt-defer/`

**职责**：在对话中把任务推到滴答清单的「任务池」

### 触发方式

| 触发方式 | 示例 |
|---------|------|
| 自然语言 | "这个推到待办"、"明天再做这个"、"这个丢到池子里" |
| 命令 | `/tt-defer <任务描述>` |
| Plan/Spec 完成后 | 生成 plan 后主动询问"要现在执行还是推到待办？" |

### 核心流程

```
用户触发 → 提取当前上下文（plan/spec/文章/任务描述）
  ↓
推断任务类型 + 组装任务格式（Markdown 结构）
  ↓
推送到滴答清单「任务池」项目（带上对应 tag）
  ↓
确认推送结果
```

### 关键能力

- **自动捕获上下文**：如果当前会话中有已生成的 plan 或 spec，自动提取完整内容作为任务的执行计划
- **智能推断 tag**：根据上下文自动推断任务类型 tag（plan-exec / spec-dev / research 等）
- **指定执行时间**：支持"明天做"、"下周做"等时间表达式，设置 dueDate
- **输出风格**：延续 tt skill 的轻松语气

### 示例场景

用户用 superpowers 生成了一个 plan 后：
> "这个 plan 先推到待办吧，明天晚上让远程跑"

tt-defer 自动：
1. 提取 plan 全文
2. 组装任务格式，自动打上 `plan-exec` tag
3. 推到滴答清单「任务池」
4. 回复："已丢进池子，远程会处理"

## tt-worker skill（执行端）

**位置**：`plugins/ticktick-manager/tt-worker/`

**职责**：远程服务器读取「任务池」中的任务并自动执行

**运行环境**：远程服务器（地址可配置），通过 SSH 或本地 Claude Code 会话触发

### 核心流程

```
启动 → 读取「任务池」中所有未完成任务
  ↓
按优先级/到期时间排序
  ↓
逐个执行：
  ├─ 读取任务 tag 确定执行策略
  ├─ 解析 content 中的执行计划
  ├─ 校验执行环境（仓库是否存在、分支是否有效）
  ├─ 进入对应仓库目录
  ├─ 根据 tag 策略执行任务
  ├─ 在 content 中记录执行进度
  └─ 执行完成后标记任务为已完成
  ↓
全部完成 → 输出本次执行报告
```

### 执行策略映射（基于 tag）

| Tag | 执行动作 | 完成标志 |
|-----|---------|---------|
| `plan-exec` | 读取 content 中的 plan，逐步执行 | plan 中所有步骤完成 |
| `spec-dev` | 读取 content 中的 spec，按 spec 开发 | 代码提交 + 测试通过 |
| `research` | 搜索资料、分析、输出报告 | 报告文档生成 |
| `article` | 抓取文章内容、提炼要点 | 摘要写入 Obsidian |
| `code-task` | 根据 content 中的描述直接编码 | 代码提交 |

### 任务状态追踪与恢复

每个任务的 content 末尾由 tt-worker 自动维护执行进度：

```markdown
## 执行记录（tt-worker 自动维护）
- [x] 步骤 1：初始化项目结构 - 2026-04-05 02:15 完成
- [x] 步骤 2：实现核心逻辑 - 2026-04-05 02:22 完成
- [ ] 步骤 3：编写测试 - 进行中...
```

**恢复机制**：
- tt-worker 重新运行时，检查 content 中的 `## 执行记录` 区块
- 已完成的步骤（`[x]`）跳过，从第一个未完成步骤（`[ ]`）继续
- 无执行记录的任务从头开始执行
- 超时中断的任务保留进度，下次可恢复

### 安全机制

| 机制 | 说明 |
|------|------|
| 任务上限 | 单次最多执行 N 个任务（可配置，默认 5） |
| 超时保护 | 单个任务最长执行时间（可配置，默认 30 分钟），超时后保留进度、不标记完成 |
| 跳过策略 | 内容不完整、无法解析、仓库不存在的任务跳过，不标记完成 |
| 执行报告 | 每次运行结束后输出：成功 N 个、跳过 N 个、失败 N 个 |

### 任务完成流程

1. 在任务 content 末尾追加 `## 执行结果` 区块（成功/失败/产出物位置）
2. 更新执行进度状态为全部 `[x]`
3. 标记滴答清单任务为已完成
4. 输出本次运行汇总

### 输出风格

`tt-worker` 作为自动化执行端，使用**简洁日志风格**（与 tt-defer 的轻松语气不同）：
- 每个任务一行摘要：`[完成] 按plan重构auth模块 - 产出: 3 commits`
- 跳过/失败的任务说明原因：`[跳过] 仓库不存在: /path/to/repo`
- 最终汇总：`本次执行: 3 成功, 1 跳过, 0 失败`

## 共享配置

### 配置文件位置

```
~/.config/tt-auto/config.json
```

首次运行时自动创建，两个 skill 共享同一份配置。

### 配置格式

```json
{
  "poolProjectId": null,
  "poolProjectName": "任务池",
  "remoteServer": null,
  "maxTasksPerRun": 5,
  "taskTimeoutMinutes": 30
}
```

| 配置项 | 说明 | 默认值 |
|-------|------|-------|
| `poolProjectId` | 任务池清单 ID | 首次自动获取后写入 |
| `poolProjectName` | 任务池清单名称 | `"任务池"` |
| `remoteServer` | 远程服务器地址（仅 tt-worker） | `null`（需用户配置） |
| `maxTasksPerRun` | 单次执行任务上限 | `5` |
| `taskTimeoutMinutes` | 单任务超时（分钟） | `30` |

两个 skill 放在现有 `ticktick-manager` plugin 下，属于滴答清单生态。

## 后续扩展方向

- **定时调度**：用户自行配置 cron 或类似机制定时触发 tt-worker
- **任务优先级**：支持紧急/普通/低优先级，影响执行顺序
- **结果通知**：任务完成后通过指定渠道通知用户
- **更多任务类型**：随着使用场景增加，扩展新的 tag 和执行策略
