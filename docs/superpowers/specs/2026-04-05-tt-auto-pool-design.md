# 滴答清单自动化任务池设计

> 将滴答清单作为「任务池」，本地推送任务、远程自动执行的异步工作架构

## 背景

本地 MacBook Air（M2）性能有限，无法同时承载大量任务。需要一个机制将不急于执行的任务推送到池子中，由远程服务器在合适的时间自动完成。

滴答清单天然适合作为这个池子 — 已有完善的 tt skill 和 tt-cli 基础设施，任务天然带有结构化信息。

## 核心架构

```
┌─────────────────────┐          ┌──────────────────────┐
│   本地 MacBook Air   │          │    远程服务器（可配置）  │
│                     │          │                      │
│  ┌───────────────┐  │          │  ┌────────────────┐  │
│  │  tt-defer     │──┼── 推 ──→ │  │  滴答清单       │  │
│  │  (推送端)      │  │          │  │  「待办清单」    │  │
│  └───────────────┘  │          │  └───────┬────────┘  │
│                     │          │          │ 读         │
│  使用场景：          │          │  ┌───────▼────────┐  │
│  - 生成 plan 后推    │          │  │  tt-worker     │  │
│  - 生成 spec 后推    │          │  │  (执行端)       │  │
│  - 文章/调研推       │          │  └────────────────┘  │
│  - 任何延迟任务      │          │                      │
└─────────────────────┘          └──────────────────────┘
```

## 任务格式

推到滴答清单的任务需自带完整上下文，因为远程执行时没有原始对话。

### 滴答清单任务结构

**标题**：简短描述做什么（≤15 字）

**内容（Markdown）**：

```markdown
## 任务类型
plan-execution / spec-development / research / article / code-task

## 执行环境
仓库路径：/path/to/repo
分支：feature-xxx（可选）

## 执行计划
（完整的 plan 或 spec 内容直接贴在这里）

## 预期产出
描述期望的产出物

## 备注
额外说明
```

### 任务类型与执行策略

| 任务类型 | 执行方式 | 完成标志 | 示例 |
|---------|---------|---------|------|
| `plan-execution` | 按 plan 逐步执行代码 | plan 中所有步骤完成 | "按 plan 重构 auth 模块" |
| `spec-development` | 根据 spec 开发新功能 | 代码提交 + 测试通过 | "按 spec 开发用户管理页" |
| `research` | 调研分析并输出报告 | 报告文档生成 | "分析 PaperWM 适用性" |
| `article` | 阅读文章并提炼要点 | 摘要写入 Obsidian | "阅读并总结某技术文章" |
| `code-task` | 通用代码任务 | 代码提交 | "修复某个 bug" |

## tt-defer skill（推送端）

**位置**：`plugins/ticktick-manager/tt-defer/`

**职责**：在对话中把任务推到滴答清单的「待办清单」

### 触发方式

| 触发方式 | 示例 |
|---------|------|
| 自然语言 | "这个推到待办"、"明天再做这个"、"这个丢到池子里" |
| 命令 | `/tt-defer <任务描述>` |
| Plan/Spec 完成后 | 生成 plan 后主动询问"要现在执行还是推到待办？" |

### 核心流程

```
用户触发 → 提取当前上下文（plan/spec/文章/任务描述）
  ↓
组装任务格式（Markdown 结构）
  ↓
推送到滴答清单「待办清单」项目
  ↓
确认推送结果
```

### 关键能力

- **自动捕获上下文**：如果当前会话中有已生成的 plan 或 spec，自动提取完整内容作为任务的执行计划
- **智能推断任务类型**：根据上下文判断是 plan-execution / spec-development / research 等
- **指定执行时间**：支持"明天做"、"下周做"等时间表达式，设置 dueDate
- **输出风格**：延续 tt skill 的轻松语气

### 示例场景

用户用 superpowers 生成了一个 plan 后：
> "这个 plan 先推到待办吧，明天晚上让远程跑"

tt-defer 自动：
1. 提取 plan 全文
2. 组装任务格式，类型标记为 `plan-execution`
3. 推到滴答清单「待办清单」
4. 回复："已丢进池子，远程会处理"

## tt-worker skill（执行端）

**位置**：`plugins/ticktick-manager/tt-worker/`

**职责**：远程服务器读取「待办清单」中的任务并自动执行

**运行环境**：远程服务器（地址可配置），通过 SSH 或本地 Claude Code 会话触发

### 核心流程

```
启动 → 读取「待办清单」中所有未完成任务
  ↓
按优先级/到期时间排序
  ↓
逐个执行：
  ├─ 解析任务类型和执行计划
  ├─ 进入对应仓库目录
  ├─ 根据 plan/spec/描述执行任务
  ├─ 执行完成后标记滴答清单任务为已完成
  └─ 在任务内容中追加执行结果摘要
  ↓
全部完成 → 输出本次执行报告
```

### 执行策略映射

| 任务类型 | 执行动作 | 完成标志 |
|---------|---------|---------|
| `plan-execution` | 读取 content 中的 plan，逐步执行 | plan 中所有步骤完成 |
| `spec-development` | 读取 content 中的 spec，按 spec 开发 | 代码提交 + 测试通过 |
| `research` | 搜索资料、分析、输出报告 | 报告文档生成 |
| `article` | 抓取文章内容、提炼要点 | 摘要写入 Obsidian |
| `code-task` | 根据 content 中的描述直接编码 | 代码提交 |

### 安全机制

| 机制 | 说明 |
|------|------|
| 任务上限 | 单次最多执行 N 个任务（可配置，默认 5） |
| 超时保护 | 单个任务最长执行时间（可配置，默认 30 分钟） |
| 跳过策略 | 内容不完整或无法解析的任务跳过，不标记完成 |
| 执行报告 | 每次运行结束后输出：成功 N 个、跳过 N 个、失败 N 个 |

### 任务完成流程

1. 标记滴答清单任务为已完成
2. 在任务 content 末尾追加 `## 执行结果` 区块（成功/失败/产出物位置）
3. 输出本次运行汇总

## 共享配置

tt-defer 和 tt-worker 共享的配置项：

| 配置项 | 说明 | 默认值 |
|-------|------|-------|
| 待办清单 projectId | 滴答清单中的项目 ID | 首次自动获取后缓存 |
| 远程服务器地址 | 仅 tt-worker 使用 | 用户自行配置 |
| 单次任务上限 | 仅 tt-worker 使用 | 5 |
| 单任务超时 | 仅 tt-worker 使用 | 30 分钟 |

## 文件结构

```
plugins/ticktick-manager/
├── tt/                    # 现有 tt skill（不变）
│   ├── SKILL.md
│   └── references/
│       ├── humanization.md
│       └── project-mapping.md
├── tt-defer/              # 新增：推送端
│   ├── SKILL.md
│   └── references/
│       └── task-format.md  # 共享的任务格式规范
└── tt-worker/             # 新增：执行端
    ├── SKILL.md
    └── references/
        └── task-format.md  # 同一份任务格式规范
```

两个 skill 放在现有 `ticktick-manager` plugin 下，属于滴答清单生态。

## 后续扩展方向

- **定时调度**：用户自行配置 cron 或类似机制定时触发 tt-worker
- **任务优先级**：支持紧急/普通/低优先级，影响执行顺序
- **结果通知**：任务完成后通过指定渠道通知用户
- **更多任务类型**：随着使用场景增加，扩展新的任务类型
