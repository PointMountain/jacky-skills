# Durable 模式

> Durable 是一种面向长任务的无人值守执行模式：任务启动后，Agent 尽量依靠默认配置和自主判断持续推进，不等待用户反复确认，尤其适合在夜间运行。

Durable 的第一性目标不是让 Agent 连续运行更久，而是把用户从等待和盯守中释放出来，同时让昂贵步骤、预计耗时、当前进度和人工接管点保持可见。无人值守不等于失去掌控；真正的 Durable 应该同时提供轻松感、可预测性和时间主权。

## 一、Durable 是什么意思

这里的 **Durable** 不是某个模型、软件版本或具体工具，而是一份任务执行约定。

当用户说“用 Durable 执行”“今晚 Durable 跑一下”或类似表达时，应理解为：

1. 这是一个可能持续较长时间的任务。
2. 用户暂时不会守在任务旁边，也不希望执行过程中频繁被提问。
3. Agent 应优先使用项目现有的默认版本、稳定配置和推荐方案。
4. 遇到普通的不确定性时，Agent 应自行做出合理判断、记录假设并继续执行。
5. 遇到可恢复的失败时，Agent 应先诊断、重试或采用安全的替代方案，而不是立即停下来等待用户。
6. 任务结束后，Agent 应给出结果、验证情况、重要决策以及仍未解决的问题。
7. 中间文档、设计记录和阶段总结只作为恢复证据，不形成用户确认门。
8. 人工验收应集中在最终可回归产物：可点击网页、可观看 E2E 视频、可调用 Skill 或可复制运行命令。

一句话概括：

> **Durable = 启动后尽量不中断、少打扰、能自我推进并留下完整结果的无人值守长任务模式。**

### 1.1 “准备进入”不等于“立即执行”

用户使用 Durable 一词时，必须区分两种意图：

- “把任务准备成 Durable”“进入 Durable 状态”：只完成目标、权限、验收契约和耗时预估，任务停在 `canDurable`，等待用户安排执行时间。
- “开始 Durable”“今晚用 Durable 跑”：明确授权启动无人值守执行，任务进入 `doing`。

账号、凭据、环境权限和方案确认只代表前置条件具备，不自动代表“现在开始”。除非用户明确同时要求“准备好并立即执行”，否则进入 `canDurable` 后必须停止并说明尚未启动。

## 二、默认执行规则

进入 Durable 模式后，Agent 默认遵循以下规则：

### 2.1 直接开始

只有用户已经明确要求“开始/执行 Durable”，并且目标和范围足够明确时，才直接执行，不再重复询问“是否开始”。如果用户只要求准备到 Durable 状态，则完成准备度检查和耗时预估后停止。

### 2.2 POC 必须单独确认

POC 不是 Durable 的免费准备步骤。开始任何 POC 前，Agent 必须说明它要消除的不确定性、预计耗时、验证边界、外部副作用和跳过 POC 的替代路径，并得到用户明确确认。

POC 在 `shaping` 阶段内执行。POC 通过只说明任务可以使用 `poc-passed` 进入 `canDurable`，不代表用户已经授权进入 `doing`。到达预估上限或验证范围扩大时必须停止并重新估时。

### 2.3 优先采用默认值

需要在多个普通选项之间选择时，按以下顺序处理：

1. 使用用户已经指定的默认值。
2. 使用项目当前已有的配置和版本。
3. 使用工具官方或项目推荐的稳定默认值。
4. 如果仍需判断，选择风险较低、容易回退的方案，并在结果中说明。

“默认版本”通常指当前项目或工具采用的稳定默认版本，不等于擅自升级到最新版本。

### 2.4 减少阻塞式提问

普通实现细节、可逆选择和低风险分歧，由 Agent 自主决定。执行期间可以记录进度，但不应要求用户立即回复才能继续。

只有当缺少的信息会明显改变任务目标，或者继续操作需要新的权限时，才应暂停并说明阻塞原因。

### 2.5 持续推进

Agent 应把长任务拆分为可验证的阶段，逐步执行。出现失败时，优先：

1. 收集错误信息并判断原因。
2. 在安全范围内重试。
3. 尝试风险较低的替代路径。
4. 保存已经完成的结果和当前状态。
5. 确实无法继续时，再停止并清楚报告阻塞点。

### 2.6 完成后验证

Durable 任务不能只以“命令运行过”作为完成标准。应根据任务类型执行必要的检查，例如测试、构建、状态检查、输出文件检查或实际功能验证。

### 2.7 提前约定最终验收

进入无人值守执行前，先明确最终产物和用户最短回归动作。不要把每个阶段的文档或报告设为人工验收门。

- 网页：提供已部署 URL，或一条启动命令与固定本地 URL。
- E2E：提供实际点击步骤、录屏和视频报告。
- Skill：提供用户可直接复制的触发提示词与预期行为。
- CLI/API：提供可复制命令、预期输出和自动测试结果。
- 文档：完成自动检查后直接交付；除非用户明确要求逐段审阅，否则不暂停等待。

### 2.8 保存执行记录

执行期间保留必要的高层记录：

- 使用了哪些 Skills/工具以及用途；
- 关键决策、假设和选择理由；
- 问题、诊断、重试与解决办法；
- 验证证据；
- 可以进一步提效的步骤。

这些记录用于任务恢复与流程优化，不要求用户在中途阅读。

## 三、Durable 不代表什么

Durable 的“无人值守”不会扩大用户原本授予的权限，也不代表 Agent 可以进行任何操作。

以下行为仍然需要用户明确授权，不能因为处于 Durable 模式就自行执行：

- 删除重要数据或进行难以恢复的破坏性操作。
- 产生费用、购买服务或扩大资源用量。
- 向外部人员发送消息、公开发布内容或创建正式发布。
- 修改生产环境中的高风险配置。
- 绕过安全限制、权限控制或既定审批流程。
- 将任务范围扩展到用户没有指定的系统、仓库或账号。

如果任务必须依赖上述操作才能继续，Agent 应保留当前进度，说明所需授权，并等待用户回来处理。

## 四、适用场景

Durable 特别适合：

- 夜间运行测试、构建、迁移或批处理任务。
- 长时间代码生成、重构、资料整理或内容处理。
- 需要多轮诊断、重试和验证的工程任务。
- 用户已经给出清晰目标，但不想持续参与过程选择的任务。
- 用户准备离线或睡觉，第二天只回归最终页面、视频或可执行产物的任务。

Durable 并不只限于晚上。只要用户希望任务在较少交互的情况下持续执行，任何时间都可以使用。

## 五、不适用场景

以下情况不适合直接进入 Durable 模式：

- 用户还在讨论方向，尚未确定要执行什么。
- 不同方案会产生明显不同的产品结果，且没有合理默认项。
- 任务一开始就需要高风险操作或新的外部授权。
- 缺少账号、凭据、文件或环境，导致任务根本无法启动。

## 六、推荐的触发表达

用户可以直接这样说：

```text
这个任务用 Durable 执行。
```

也可以补充范围或结束条件：

```text
今晚用 Durable 把测试修到全部通过，使用项目默认版本，不要中途等我回复。
```

Agent 看到 **Durable** 后，应自动采用本文约定；除非用户在当次任务中给出了更具体、与本文不同的指令，以用户当次指令为准。

## 七、完成报告

Durable 任务结束时，至少应说明：

1. 最终结果是否完成。
2. 实际修改或产出了什么。
3. 做过哪些关键验证。
4. 自主采用了哪些重要默认值或假设。
5. 是否还存在失败项、风险或需要用户处理的阻塞点。

## 总结

Durable 的核心不是“无限运行”，而是让一个目标明确的长任务在用户不值守时，仍能按照安全边界自主选择默认方案、处理普通问题、持续推进并完成验证。

在本仓库的后续交流中，用户单独提到 **Durable**，默认就是指本文定义的执行模式。
