# 技术文档写作质量规范

> 沉淀到 Obsidian 的每篇文章都应成为**可独立使用**的知识单元。本规范定义写作质量底线和进阶标准。

## 核心原则

| 原则 | 含义 | 对应低分教训 |
|------|------|-------------|
| **有料** | 每段都有信息增量，拒绝水话 | 4 篇"太浅/无干货"低分 |
| **准确** | 标题即内容，不含糊不夸大 | 2 篇"标题不匹配"低分 |
| **可操作** | 读者看完能直接用 | 唯一 8 分文章是操作指南 |
| **有根** | 观点有出处，代码有链接，结论有依据 | 缺 reference 扣分 |
| **连贯** | 与相关文章形成知识网络 | 孤立文章价值低 |

## 文章类型与质量标准

沉淀时先判断文章类型，不同类型有不同的必填要素。

### 类型 A：概念/分析

> 讨论架构设计、技术选型、原理剖析、方案对比

**必填要素**：
- 一句话说清这篇文章解决什么问题
- 独到分析角度（不能只是"X 是什么"的表面介绍）
- 关键论点有代码引用或设计意图支撑
- "参见"链接到相关文章或官方文档

**写作模板**：
```markdown
# {主题}

> 一句话：这篇文章解决了什么问题 / 提供了什么视角

## 背景 / 为什么关注
// 3-5 句交代上下文，让读者知道为什么这个话题重要

## 核心内容
// 正文，按逻辑分段，每段有信息增量

## 关键决策 / 设计亮点
// 如果涉及方案选择，列出决策点和理由

## 参考
- [[相关文章]]
- [官方文档](url)
```

### 类型 B：操作指南

> 步骤性内容：安装配置、发布流程、使用教程

**必填要素**：
- 前置条件（读者需要什么才能开始）
- 编号步骤（1. 2. 3. 每步只做一件事）
- 关键步骤有代码/命令示例
- 常见问题或踩坑预警
- 验证方法（怎么确认操作成功）

**写作模板**：
```markdown
# {做什么事情}

> 一句话说明这篇指南的目标

## 前置条件
- 列出需要提前准备的东西

## 步骤

### 1. 第一步
具体操作 + 代码/命令示例

### 2. 第二步
...

## 常见问题
| 问题 | 原因 | 解决方案 |
|------|------|----------|

## 验证
怎么确认操作成功
```

### 类型 C：踩坑记录

> Bug 排查、兼容性问题、意外行为

**必填要素**：
- 症状描述（怎么发现的）
- 根因分析（为什么发生）
- 解决方案（怎么修的）
- 预防措施（怎么避免再犯）

**写作模板**：
```markdown
# {问题简述}

## 症状
具体表现，附错误信息/截图描述

## 根因
为什么会发生，分析过程

## 解决方案
具体修复步骤

## 预防
如何避免类似问题

> [!code-ref] 相关代码（如适用）
```

### 类型 D：决策记录（ADR）

> "为什么选 X 不选 Y" 的技术选型/方案决策

**必填要素**：
- 决策背景
- 备选方案（至少 2 个）
- 对比维度
- 最终选择及理由
- 影响范围

**写作模板**：
```markdown
# {决策标题}

## 背景
为什么要做这个决策

## 备选方案
### 方案 A：{名称}
- 优点
- 缺点

### 方案 B：{名称}
- 优点
- 缺点

## 决策
选择 {方案}，因为 {理由}

## 影响
这个决策影响了哪些模块/功能
```

## 写作风格规则

### 做到的

| 规则 | 示例 |
|------|------|
| **用具体代替抽象** | "响应时间从 3s 降到 200ms" > "性能大幅提升" |
| **先结论后展开** | 每段先给结论，再展开解释 |
| **技术术语附简短解释** | "SEA（Single Executable Application，单文件可执行应用）" |
| **代码用 code-ref** | 不嵌入代码，用 `> [!code-ref]` 引用 |
| **文章间用 `[[wikilinks]]`** | 同主题文章互相引用 |
| **包含 reference** | 底部附官方文档/相关链接 |

### 禁止的

| 反模式 | 为什么 | 正确做法 |
|--------|--------|----------|
| **链接堆砌** | 读者不知道重点 | 每个链接附 1-2 句说明为什么推荐 |
| **标题党** | "高阶技巧"实际是基础操作 | 标题准确反映内容深度 |
| **拼凑文章** | 多个不相关主题混一篇 | 一篇一主题，拆分写 |
| **表面介绍** | "X 是一个很好的工具" | 写出具体好在哪里、怎么用 |
| **无头无尾** | 开头没有背景，结尾没有总结 | 开头 1 句话说目的，结尾附参考 |
| **纯代码无解释** | 只贴代码没有上下文 | 代码用 code-ref，文字说设计意图 |

## 质量自检清单

写入文章前，对照以下清单逐项检查：

- [ ] **Frontmatter 完整**：tags（非空数组）、type（必须是预定义值之一：concept/tutorial/troubleshooting/learning/reference/note）、updated_at（有效日期）
- [ ] **标题准确**：读者看标题就知道文章讲什么
- [ ] **有信息增量**：不是搜索引擎第一条就能找到的内容
- [ ] **结构完整**：有开头（背景/目的）、有正文、有收尾（参考/总结）
- [ ] **深度足够**：至少有一个"原来如此"的 insight
- [ ] **代码有引用**：涉及代码时用 code-ref，不嵌入
- [ ] **有参考链接**：底部附相关文档或 `[[wikilinks]]`
- [ ] **无敏感信息**：API key / 密码 / token → `{REDACTED}`

### 质量分级

| 等级 | 标准 | 行动 |
|------|------|------|
| **优秀（≥8）** | 独到视角 + 可操作 + 有深度 + 有参考 | 直接写入 |
| **良好（6-7）** | 有内容但缺某项（如缺参考、结构可优化） | 写入，标注待补充 |
| **一般（3-5）** | 有信息但太浅或结构差 | 补充深度后再写入 |
| **差（≤2）** | 无干货、拼凑、标题不匹配 | 不写入，告知用户 |

## 与 rating-preferences 的关系

`writing-quality.md` 定义**写作时的质量标准**（写入前检查）。
`.rating-preferences.md` 记录**历史评分反馈 + 自动学习的偏好**（持续演进）。

三文件形成**偏好自学习闭环**：

```
对话中用户表达偏好
  → 偏好自学习步骤捕获信号
  → 更新 .rating-preferences.md
  → 下次沉淀时读取偏好文件
  → 写入质量更高、更贴合用户风格的文章
  → 再次捕获新的偏好信号
  → ...
```
