# 仓库学习维度参考

> 学习一个仓库时，知识按主题维度组织，而非按时间。以下是完整的维度清单，用于分析对话内容并归类。

## 维度清单

### 1. 架构设计
**信号**：讨论模块划分、目录结构、数据流、技术栈、设计理念

典型内容：
- 项目概述（解决什么问题）
- 目录结构与模块职责
- 核心数据流（输入→处理→输出）
- 技术栈选型及理由
- 设计亮点与权衡

文件命名：`architecture.md`、`data-flow.md`、`tech-stack.md`

### 2. 核心机制
**信号**：讨论数据结构、构建流程、解析逻辑、搜索算法、增量更新

典型内容：
- 核心数据结构定义
- 关键算法和处理流程
- 注册表/插件机制
- 缓存与增量更新策略
- 性能优化手段

文件命名：`core-mechanism.md`、`build-pipeline.md`、`search-system.md`

### 3. 功能与模式
**信号**：讨论功能设计、接口设计、协作关系、模板格式、可复用模式

典型内容：
- 功能清单与职责
- 功能间协作关系
- 统一的接口/模板格式
- 知识注入与扩展机制
- 可复用设计模式清单

文件命名：`skill-patterns.md`、`api-design.md`、`extension-system.md`

### 4. 适配与生态
**信号**：讨论平台差异、安装方式、兼容性、多环境支持

典型内容：
- 支持的平台/环境
- 各平台差异与安装机制
- 配置文件差异
- 降级与兜底策略

文件命名：`multi-platform.md`、`compatibility.md`、`deployment.md`

### 5. 设计规范
**信号**：讨论命名规则、编码约束、文件组织约定、版本管理规则

典型内容：
- 命名规范
- 目录结构约定
- 版本管理规则
- 测试规范

文件命名：`conventions.md`、`naming-rules.md`、`versioning.md`

### 6. 方案决策
**信号**：讨论技术选型、方案取舍、架构决策、为什么用 X 不用 Y

典型内容：
- 决策背景
- 备选方案
- 选择理由
- 影响范围

文件命名：`decisions.md`、`adr-{topic}.md`

### 7. 踩坑记录
**信号**：遇到 bug、排查问题、兼容性坑、意外行为

典型内容：
- 问题症状
- 根因分析
- 解决方案
- 预防措施

文件命名：`troubleshooting.md`、`pitfalls.md`

### 8. 未来展望
**信号**：提到待办、计划、改进想法、下一步、TODO

典型内容：
- 待完成功能
- 改进计划
- 技术债务
- 新想法

文件命名：`roadmap.md`、`todo.md`、`ideas.md`

### 9. 代码引用（Code Reference）
**信号**：讨论了具体代码文件、函数实现、行号级别的细节

典型内容：
- 关键函数/类的实现位置和设计意图
- 核心算法所在的文件和行号
- 值得复用的代码模式及其位置
- 架构关键节点的代码实现

**重要规则**：代码不嵌入笔记，而是使用 code-ref callout 引用。详见 [code-ref-format.md](code-ref-format.md)。

何时使用 code-ref：
- 对话中提到了具体文件路径和代码实现
- 讨论了某个函数/类/模块的设计
- 发现了值得日后复用的代码模式

何时不需要 code-ref：
- 纯概念/设计讨论，未涉及具体代码
- 配置片段（如 JSON/YAML），简短且不太会变化
- 伪代码或算法描述（非实际项目代码）

## 使用方式

分析对话内容时：
1. 识别对话涉及哪些维度
2. 匹配已有文件或新建文件（slug 从维度主题生成）
3. 每个维度可能有多个文件（如 `architecture.md` 和 `data-flow.md`）
4. 不要求每次对话都覆盖所有维度，有就提取，没有就跳过
5. **涉及具体代码时**，生成 code-ref callout 而非嵌入代码片段（详见 [code-ref-format.md](code-ref-format.md)）
