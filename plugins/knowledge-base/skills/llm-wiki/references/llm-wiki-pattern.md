# LLM Wiki

一种使用 LLM 构建个人知识库的模式。

这是一个理念文件，设计为可以直接复制粘贴给你的 LLM Agent（如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达高层思路，而你的 Agent 会与你协作搭建具体实现。

## 核心理念

大多数人使用 LLM 处理文档的体验类似于 RAG：你上传一组文件，LLM 在查询时检索相关片段，然后生成回答。这能工作，但 LLM 每次都在从头重新发现知识。没有积累。问一个需要综合五篇文档的微妙问题，LLM 每次都得找到并拼接相关片段。什么都没有沉淀下来。NotebookLM、ChatGPT 文件上传和大多数 RAG 系统都是这种模式。

这里的想法不同。LLM 不是在查询时从原始文档中检索，而是**增量地构建和维护一个持久化的 wiki** —— 一个结构化的、互相链接的 Markdown 文件集合，位于你和原始资料之间。当你添加新的资料时，LLM 不只是索引它以备后续检索。它会阅读它、提取关键信息，并将其整合到现有的 wiki 中 —— 更新实体页面、修订主题摘要、标注新数据与旧声明的矛盾之处、强化或挑战不断演进的综合分析。知识被编译一次，然后*持续保持最新*，而不是在每次查询时重新推导。

这是关键差异：**wiki 是一个持久化的、复利增长的知识产物。** 交叉引用已经建立。矛盾已经被标记。综合分析已经反映了你读过的所有内容。wiki 随着你添加的每一个来源和提出的每一个问题而不断丰富。

你从不（或极少）自己编写 wiki —— LLM 编写和维护所有内容。你负责策展来源、探索方向和提出正确的问题。LLM 承担所有繁琐的工作 —— 总结、交叉引用、归档和簿记，这些才使知识库随着时间推移真正有用。在实践中，我一边开着 LLM Agent，一边开着 Obsidian。LLM 根据我们的对话进行编辑，我实时浏览结果 —— 跟着链接点进去、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE；LLM 是程序员；wiki 是代码库。

这可以应用于很多不同的场景。举几个例子：

- **个人**：追踪自己的目标、健康、心理、自我提升 —— 归档日记条目、文章、播客笔记，随时间构建关于自己的结构化画像。
- **研究**：在数周或数月内深入一个主题 —— 阅读论文、文章、报告，增量地构建一个带有演进论点的综合 wiki。
- **阅读书籍**：边读边逐章归档，构建角色、主题、情节线索的页面以及它们之间的关联。读到最后你就有了一个丰富的伴读 wiki。类似 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) —— 数千个互相链接的页面，涵盖角色、地点、事件、语言，由志愿者社区历时多年建成。你可以在阅读时由 LLM 完成所有交叉引用和维护工作，个人构建出类似的东西。
- **商业/团队**：由 LLM 维护的内部 wiki，喂入 Slack 线程、会议记录、项目文档、客户通话。可能有人在环中审核更新。wiki 保持最新，因为 LLM 做了团队中没人愿意做的维护工作。
- **竞争分析、尽职调查、旅行规划、课程笔记、爱好深潜** —— 任何需要随时间积累知识并希望它有组织而非散乱的场景。

## 架构

分为三层：

**原始资料层** —— 你策划的源文档集合。文章、论文、图片、数据文件。这些是不可变的 —— LLM 从中读取但从不修改。这是事实来源。

**Wiki 层** —— LLM 生成的 Markdown 文件目录。摘要、实体页面、概念页面、对比、概述、综合分析。LLM 完全拥有这一层。它创建页面、在新资料到来时更新它们、维护交叉引用，并保持一切一致。你阅读它；LLM 编写它。

**Schema 层** —— 一个文档（如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM wiki 的结构、约定是什么，以及在摄入资料、回答问题或维护 wiki 时应遵循的工作流。这是关键的配置文件 —— 正是它使 LLM 成为一个有纪律的 wiki 维护者而非通用聊天机器人。你和 LLM 随时间共同演进这个文件，随着你发现什么在你的领域中有效。

## 操作

**摄入（Ingest）。** 你将新资料放入原始集合，告诉 LLM 处理它。一个示例流程：LLM 阅读来源、与你讨论关键要点、在 wiki 中写一个摘要页、更新索引、更新 wiki 中相关的实体和概念页面，并追加一条日志。一个来源可能影响 10-15 个 wiki 页面。我个人倾向于逐个摄入并保持参与 —— 我阅读摘要、检查更新、引导 LLM 重点关注什么。但你也可以一次性批量摄入多个来源，减少监督。由你来开发适合自己风格的工作流，并在 schema 中记录以供后续会话使用。

**查询（Query）。** 你向 wiki 提问。LLM 搜索相关页面，阅读它们，并综合出一个带引用的回答。回答可以根据问题采取不同形式 —— 一个 Markdown 页面、一个对比表格、一个幻灯片（Marp）、一个图表（matplotlib）、一个画布。一个重要的洞察：**好的回答可以作为新页面归档回 wiki。** 你要求的对比、一项分析、你发现的关联 —— 这些都是有价值的，不应该消失在聊天记录中。这样你的探索就会像摄入的来源一样在知识库中复利增长。

**检查（Lint）。** 定期让 LLM 对 wiki 进行健康检查。查找：页面之间的矛盾、被新资料淘汰的过时声明、没有入链的孤立页面、被提及但缺少独立页面的重要概念、缺失的交叉引用、可以通过网络搜索填补的数据空白。LLM 擅长建议新的研究问题和新的资料来源。这让 wiki 在增长过程中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（和你）在 wiki 增长过程中进行导航。它们服务于不同目的：

**index.md** 是内容导向的。它是 wiki 中所有内容的目录 —— 每个页面列出链接、一行摘要，以及可选的元数据如日期或来源数量。按类别组织（实体、概念、来源等）。LLM 在每次摄入时更新它。回答查询时，LLM 先读取索引找到相关页面，然后深入阅读。这在中等规模下（约 100 个来源、数百个页面）出奇地有效，避免了基于嵌入向量的 RAG 基础设施的需求。

**log.md** 是按时间顺序的。它是一个只追加的记录，记录了发生了什么以及何时发生 —— 摄入、查询、检查。一个有用的技巧：如果每个条目以一致的前缀开头（如 `## [2026-04-02] ingest | 文章标题`），日志就可以用简单的 Unix 工具解析 —— `grep "^## \[" log.md | tail -5` 给你最近 5 条记录。日志为你提供了 wiki 演变的时间线，并帮助 LLM 了解最近做了什么。

## 可选：CLI 工具

在某个时候你可能想构建一些小工具，帮助 LLM 更高效地操作 wiki。对 wiki 页面的搜索引擎是最明显的 —— 小规模下索引文件就够了，但随着 wiki 增长你需要正式的搜索。[qmd](https://github.com/tobi/qmd) 是一个好选择：它是一个本地 Markdown 文件搜索引擎，具有混合 BM25/向量搜索和 LLM 环，全部在设备上运行。它既有 CLI（所以 LLM 可以通过 shell 调用它），也有 MCP server（所以 LLM 可以将其作为原生工具使用）。你也可以自己构建更简单的东西 —— LLM 可以在需要时帮你 vibe-code 一个简单的搜索脚本。

## 技巧与窍门

- **Obsidian Web Clipper** 是一个浏览器扩展，可以将网页文章转换为 Markdown。对于快速将资料导入原始集合非常有用。
- **下载图片到本地。** 在 Obsidian 设置 → 文件与链接中，将"附件文件夹路径"设置为固定目录（如 `raw/assets/`）。然后在设置 → 快捷键中，搜索"Download"找到"Download attachments for current file"并绑定到一个快捷键（如 Ctrl+Shift+D）。裁剪文章后按快捷键，所有图片就会下载到本地磁盘。这是可选的但很有用 —— 它让 LLM 能直接查看和引用图片，而不依赖可能会失效的 URL。注意 LLM 无法在一次读取中原生处理带有内联图片的 Markdown —— 解决方法是让 LLM 先读文本，然后单独查看部分或全部引用的图片以获取额外上下文。有点笨拙但足够好用。
- **Obsidian 的图谱视图** 是查看 wiki 形态的最好方式 —— 什么连接着什么、哪些页面是枢纽、哪些是孤岛。
- **Marp** 是一个基于 Markdown 的幻灯片格式。Obsidian 有对应的插件。可以直接从 wiki 内容生成演示文稿。
- **Dataview** 是一个 Obsidian 插件，可以对页面 frontmatter 运行查询。如果你的 LLM 在 wiki 页面中添加 YAML frontmatter（标签、日期、来源数量），Dataview 可以生成动态表格和列表。
- wiki 就是一个 Markdown 文件的 git 仓库。你免费获得版本历史、分支和协作能力。

## 为什么有效

维护知识库的繁琐部分不是阅读或思考 —— 而是簿记。更新交叉引用、保持摘要最新、标注新数据何时与旧声明矛盾、维护数十个页面的一致性。人类放弃 wiki 是因为维护负担增长快于价值。LLM 不会感到无聊、不会忘记更新一个交叉引用、可以在一次处理中触及 15 个文件。wiki 保持维护是因为维护成本接近于零。

人类的工作是策展来源、指导分析、提出好问题、思考这一切意味着什么。LLM 的工作是其他一切。

这个理念在精神上与 Vannevar Bush 的 Memex（1945）相关 —— 一个个人的、策划的知识存储，文档之间有关联轨迹。Bush 的愿景比网络最终变成的东西更接近这个想法：私有的、积极维护的、旨在增强个人思考而非向世界发布的。
