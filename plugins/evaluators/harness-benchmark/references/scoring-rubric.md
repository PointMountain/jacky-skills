# 评分标准详细文档（Scoring Rubric）

本文件包含两种评估模式的完整评分标准、权重说明和通过标准等级表。

---

## 一、前端设计评估评分标准

### D1: 设计质量（Design Quality）— 30 分

**核心问题**：设计是否感觉像一个连贯的整体，而不是部分的集合？

| 分值区间 | 判定标准 |
|----------|----------|
| 25-30 | 所有视觉元素（颜色、排版、布局、图像、动画）协同创造独特氛围和身份；整体感强烈，像专业设计师的手笔 |
| 18-24 | 大部分元素协调一致，有明确的视觉方向；个别元素游离于整体之外 |
| 10-17 | 有基本的视觉组织，但元素之间缺乏关联；看起来像拼凑的 |
| 0-9 | 无整体感可言，各部分随机堆砌 |

**检查项**：
- [ ] 色彩方案是否贯穿始终且有意义
- [ ] 排版层次（标题/正文/辅助文字）是否清晰一致
- [ ] 间距节奏是否有规律可循
- [ ] 视觉重量分布是否平衡
- [ ] 是否有明确的视觉"签名"（让人记住的设计元素）

### D2: 原创性（Originality）— 30 分

**核心问题**：是否有自定义决策的证据，还是只是模板布局、库默认值和 AI 生成的模式？

| 分值区间 | 判定标准 |
|----------|----------|
| 25-30 | 有清晰的创造性飞跃；人类设计师能识别出深思熟虑的创意选择；独特且令人难忘 |
| 18-24 | 有原创元素和自定义决策；部分仍依赖常见模式，但整体有辨识度 |
| 10-17 | 基本是已知模式的组合，但有少量个性化调整 |
| 0-9 | 纯模板输出；未修改的库存组件；AI 生成的明显标志（白底紫渐变等） |

**AI 垃圾检测清单**（命中任何一项扣 5 分）：
- 白底紫色渐变
- 千篇一律的卡片网格布局
- 系统默认字体（Inter/Roboto/Arial）无个性化处理
- 充斥通用图标库默认样式
- 明显的 Tailwind/CSS 框架痕迹（未做定制）
- 所有元素等距排列，无层次变化

**积极信号**（每项加 3 分）：
- 自定义配色方案，非框架默认
- 非对称布局或有意的空间"浪费"
- 独特的排版选择（展示字体 + 正文字体搭配）
- 微妙的视觉纹理（噪点、网格、渐变网格等）
- 打破常规的交互方式

### D3: 工艺（Craftsmanship）— 20 分

**核心问题**：技术执行是否到位？排版层次、间距一致性、色彩和谐、对比度。

| 分值区间 | 判定标准 |
|----------|----------|
| 16-20 | 技术执行精准；排版层次清晰、间距一致、色彩和谐、对比度恰当；无明显技术缺陷 |
| 10-15 | 大部分技术执行到位；有少量间距/对齐/色彩小问题 |
| 5-9 | 有明显的工艺问题但不影响使用 |
| 0-4 | 基础工艺被破坏：文字不可读、元素重叠、对齐混乱 |

**注意**：Claude 在工艺方面通常默认表现良好。此维度的意义是**底线检查**而非差异化指标。如果工艺不过关，说明基础被破坏。

### D4: 功能性（Functionality）— 20 分

**核心问题**：独立于美学，用户能否理解界面功能、找到主要操作、在不猜测的情况下完成任务？

| 分值区间 | 判定标准 |
|----------|----------|
| 16-20 | 用户能直觉式操作；主要功能路径清晰；无引导也能完成核心任务 |
| 10-15 | 基本可用；某些操作需要探索或试错才能发现 |
| 5-9 | 功能存在但交互不直观；用户需要猜测 |
| 0-4 | 核心功能无法使用或交互完全断裂 |

### 权重设计说明

```
设计质量 × 0.30 + 原创性 × 0.30 + 工艺 × 0.20 + 功能性 × 0.20 = 总分
```

**为什么设计质量和原创性权重更高？**
- Claude 在工艺和功能性方面默认已经得分很高（所需技术能力对模型来说是自然的）
- 但在设计和原创性方面，Claude 经常产生平淡的输出
- 通过加权推动模型承担更多美学风险，而非停留在安全区

### 前端设计通过标准

| 等级 | 分数 | 含义 |
|------|------|------|
| A | 90-100 | 博物馆级 — 可作为设计参考案例 |
| B | 75-89 | 专业级 — 达到产品上线标准 |
| C | 60-74 | 合格 — 基本满足需求但缺乏亮点 |
| D | 40-59 | 不合格 — 存在明显问题 |
| F | 0-39 | 失败 — 需要完全重做 |

## 二、全栈开发评估评分标准

### D1: 功能完整性（Feature Completeness）— 30 分

**核心问题**：规格中定义的功能是否都已实现且真正可用？

| 分值区间 | 判定标准 |
|----------|----------|
| 25-30 | 所有规格功能完整实现，无存根、无占位符；核心交互路径均可端到端完成 |
| 18-24 | 大部分功能完整；个别功能有存根或半成品但核心流程畅通 |
| 10-17 | 有功能但交互深度不足；表面看起来完整但使用时发现断裂 |
| 0-9 | 核心功能不可用；功能之间连接断裂；实体能出现在屏幕上但不响应输入 |

**存根检测**（每项 -3 分）：
- 按钮存在但点击无反应
- 输入框存在但无法提交
- 菜单存在但选项不工作
- 数据展示存在但无法交互（拖动、编辑、删除）
- 仅 `console.log` 而无实际逻辑

### D2: 代码质量（Code Quality）— 25 分

**核心问题**：代码是否结构清晰、可维护、遵循最佳实践？

| 分值区间 | 判定标准 |
|----------|----------|
| 21-25 | 架构清晰、模块化好、命名有意义、错误处理完善、无反模式 |
| 15-20 | 整体良好；有少量可以改进的地方但不影响维护 |
| 8-14 | 代码能工作但结构混乱；硬编码、重复代码、过深嵌套 |
| 0-7 | 技术债严重；关键逻辑难以理解和修改 |

**检查项**：
- [ ] 无硬编码的配置值（应使用环境变量或配置文件）
- [ ] 无空的 catch 块或吞掉错误
- [ ] 无未处理的 Promise（async 函数返回值未 await）
- [ ] 无魔法数字（应提取为命名常量）
- [ ] 组件/函数职责单一
- [ ] 类型定义完整（TypeScript 项目）

### D3: 用户体验（User Experience）— 25 分

**核心问题**：真实使用时，用户能否顺利完成目标任务？

| 分值区间 | 判定标准 |
|----------|----------|
| 21-25 | 操作直觉化；工作流程有引导；布局合理不浪费空间；错误状态有友好提示 |
| 15-20 | 基本可用；某些操作需要摸索；布局有小瑕疵 |
| 8-14 | 工作流程僵化但可完成；用户需要知道正确的操作顺序但界面没有引导 |
| 0-7 | 核心交互断裂；用户无法完成任务；界面令人困惑 |

**工作流检查**：
- [ ] 操作路径是否有明确引导（而非需要摸索顺序）
- [ ] 布局是否充分利用空间（而非固定高度让大区域空白）
- [ ] 错误状态是否有可操作的提示
- [ ] 加载状态是否有反馈
- [ ] 表单验证是否即时且友好

### D4: 产品深度（Product Depth）— 20 分

**核心问题**：产品是否有超出基本规格的打磨和思考？

| 分值区间 | 判定标准 |
|----------|----------|
| 16-20 | 超出规格的细节打磨；边缘情况处理完善；有惊喜的产品洞察 |
| 10-15 | 满足规格要求，无更多也无更少 |
| 5-9 | 规格中的部分要求被简化或跳过 |
| 0-4 | 明显偷工减料；关键规格项被忽略 |

### 全栈开发通过标准

| 等级 | 分数 | 含义 |
|------|------|------|
| A | 85-100 | 生产就绪 — 可直接部署上线 |
| B | 70-84 | 基本可用 — 核心功能完整，有小问题需修复 |
| C | 50-69 | 需要返工 — 功能存在但质量不达标 |
| D | 30-49 | 严重不足 — 需要大量修复 |
| F | 0-29 | 失败 — 需要重新实现 |
