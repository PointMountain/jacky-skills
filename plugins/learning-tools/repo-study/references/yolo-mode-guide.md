## 1. Subagent 配置与 Prompt 模板

使用 Agent 工具启动 subagent 执行研究，主会话不直接分析源码。

**subagent 配置**：
- subagent_type: `"Explore"`（擅长代码探索和分析）
- 颜色标识：蓝色（研究任务）
- prompt 中包含：源码路径、研究问题、输出格式要求

**subagent prompt 模板**：
```
你是代码架构分析专家。请深入分析以下仓库的源码。

**源码路径**: {项目目录}/{repo-name}/
**研究问题**: {用户的研究问题}
**文档资源**: {Phase 1 扫描到的文档路径列表，如无则为空}

请使用 Glob 搜索文件、Grep 搜索关键词、Read 阅读关键文件，完成以下分析：

### 第一步：产品认知（如果有文档资源）
1. 阅读文档资源（README.md、docs/ 目录下的指南文件）
2. 提取产品形态：这是什么类型的工具？（npm 包/CLI/Web 应用/浏览器插件/桌面应用）
3. 提取基本使用方式：安装命令、第一个命令示例、输出格式
4. 提取核心组件：工具由哪些部分组成？每个部分的作用？

### 第二步：代码分析
1. **搜索相关文件**：找到与研究问题相关的核心文件
2. **阅读关键代码**：深入理解核心实现逻辑
3. **分析架构设计**：理解模块关系、调用链和数据流
4. **提取设计模式**：发现可复用的设计模式和技巧

### 第三步：前因后果分析
对每个核心技术概念/设计决策，必须回答：
1. **是什么？** — 用简单语言解释这个概念
2. **为什么需要？** — 不用这个技术会怎样？有什么痛点？
3. **怎么实现的？** — 简要说明核心实现思路
4. **替代方案对比** — 为什么不用 X 而用 Y？

**输出要求**：
- 以「让完全不懂的人也能看懂」的原则撰写
- 按层次组织：产品认知 → 核心概念(含前因后果) → 代码原理
- 包含文件路径和行号的代码引用表
- 分步骤说明实现原理
- 每个技术概念必须解释"为什么需要"
- 如果项目有文档，标注"项目已有文档可参考：{路径}"
- 如果是中文提问，使用中文输出
```

## 2. 并行研究（多课题）

当用户一次性提出多个独立研究问题时，可以启动多个 subagent 并行研究：

```
// 同时启动多个研究 subagent（每个独立课题一个）
Agent({ description: "研究课题A", prompt: "..." })  // 蓝色标识
Agent({ description: "研究课题B", prompt: "..." })  // 蓝色标识
```

**并行触发条件**：
- 用户明确提出 2 个或以上独立研究问题
- 研究问题之间没有强依赖关系
- 每个课题分配一个独立的 subagent

## 3c. 技术展示文章输出模板

**触发条件**：Phase 6 用户选择"生成技术展示文章"。

**前置条件**：至少完成过一轮研究（explorer/ 中有研究笔记）。

**写作原则**：
- 以**研究者的第三人称视角**写作（"研究了这个项目后..."）
- 面向掘金/知乎等技术社区，技术深度优先
- 有叙事弧线（6 段式），不是纯技术文档
- 有个人洞察和评价，不是纯客观转述

**详细指南** → `references/article-mode-guide.md`

### 文章生成 Subagent Prompt

```
你是一位面向技术社区的内容创作者。请根据以下研究素材，生成一篇面向掘金/知乎等技术社区的技术展示文章。

**项目名称**: {repo-name}
**项目地址**: {GitHub URL}
**研究素材**: {已有研究笔记内容摘要}
**项目文档**: {README/SKILL.md 关键内容}
**目标读者**: 有一定技术基础的开发者，对 {项目领域} 感兴趣

### 视角定位

以**深度研究者的第三人称视角**写作：
- 用"研究了这个项目后"、"让人印象深刻的是..."的角度
- 不假装是原作者，但可以提炼和总结作者的设计哲学
- 可以加入自己作为研究者的洞察和评价

### 叙事结构（必须包含 6 个阶段）

1. **惊艳开场** — 用具体场景/数字展示项目能力，引出项目名
2. **痛点共鸣** — 对比现有方案不足，列出理想方案需求
3. **快速上手** — 安装命令 + 使用场景 + 架构概览图
4. **设计哲学** — 提炼一句话设计公式，分层展开
5. **技术亮点** — 2-3 个有深度的实现剖析（含代码）
6. **开放讨论** — 提炼洞察 + 开放性问题 + 项目链接

### 技术深度要求（适配掘金/知乎）

- 代码块：关键实现必须有完整代码片段和中文注释
- 原理分析：不只说"怎么用"，要说清"为什么这样设计"
- 架构图：用 ASCII 或 Mermaid 画核心架构
- Before/After 对比：展示有无这个方案的差异

### 必须包含的内容

- 开头用具体场景/数字展示项目能力
- 对比现有方案的不足（附具体失败场景）
- 提炼项目的设计哲学（一句话公式 + 分层展开）
- 2-3 个有深度的技术实现剖析（含代码引用）
- 结尾提出开放性问题或讨论点

### 风格要求

- 技术自信但有理有据
- 有个人洞察和评价，不是纯客观转述
- 用具体代码/场景替代抽象描述
- 适当使用 emoji 和 ⬇️ 箭头引导阅读流
- 代码块使用 ``` 标注语言类型，注释使用中文

### 避免事项

- 不要写成纯技术文档或 API 说明
- 不要用"本文将介绍..."开头
- 不要罗列所有功能，只讲最有洞察的部分
- 不要缺少个人评价和设计思考

### 输出格式

完整的 Markdown 文章，可直接发布到掘金/知乎。字数 3000-5000 字。
```

### 文章输出文件

文件路径：`notes/{repo-name}-article.md`（非教程性质）

```markdown
---
title: "{项目名}：{一句话能力描述}"
date: "{生成日期}"
source_notes:
  - "{素材笔记 1 路径}"
  - "{素材笔记 2 路径}"
tags: ["技术展示", "{项目领域}"]
---

{文章正文（6 段式结构）}
```

### 质量检查

生成文章后，对照以下清单验证：

- [ ] 包含完整的 6 段叙事弧线（惊艳开场 → 痛点共鸣 → 快速上手 → 设计哲学 → 技术亮点 → 开放讨论）
- [ ] 开场有具体数字/场景
- [ ] 对比了至少 1 个现有方案不足
- [ ] 有复制即用的安装命令
- [ ] 提炼了一句话设计公式
- [ ] 有 2-3 个技术亮点（含代码分析）
- [ ] 有架构图或数据流图
- [ ] 有 Before/After 对比
- [ ] 语气自然，有研究者洞察
- [ ] 结尾有开放性问题
- [ ] 包含 GitHub 链接

## 4. 笔记沉淀

### Survey 模式：沉淀到 explorer/

将研究发现写入 `explorer/` 目录，格式同输出模板。
同步更新 `.study-meta.json` 的 `topics[]`：

- 若 topic 不存在：创建新 topic（`location: "tutorials"`）
- 若 topic 已存在：在该 topic 下追加 `questions[]` 与 `artifacts[]`
- `progress` 采用持续态统计（问题数/笔记数/指南数/skill 模板数/可运行 skill 数）
- 不维护"完成态"，默认 `state: "active"`
- 完成后设置 `surveyState = "completed"`

### Incremental 模式：沉淀到 notes/

将增量问答结果写入 `notes/` 目录。
同步更新 `.study-meta.json` 的 `topics[]`：

- 新建 topic 条目，标记 `location: "notes"`
- 不更新 `surveyState`（保持 `"completed"`）

**Incremental 模式 subagent prompt 模板**：

```
你是代码分析专家。请针对以下问题分析相关源码。

**源码路径**: {项目目录}/{repo-name}/
**研究问题**: {用户的增量问题}
**已有调研**: {explorer/ 中已有的笔记摘要，供参考避免重复}

请只分析与问题直接相关的代码区域，不需要全面分析。

**输出要求**：
- 以「让完全不懂的人也能看懂」的原则撰写
- 包含文件路径和行号的代码引用
- 如果是中文提问，使用中文输出
```

**研究日志格式（RESEARCH-LOG.md）：**

```markdown
# 研究日志

## YYYY-MM-DD: {研究主题}

**研究问题**: {用户的研究问题}

**仓库**: [REPO_NAME](GITHUB_URL)

**核心发现**:
- {发现 1}
- {发现 2}

**进度（持续更新）**:
- questions: {n}
- notes: {n}
- guides: {n}
- skill templates: {n}
- runnable skills: {n}

## 5. 翻译功能提示

**条件触发**：如果用户使用中文提问，在沉淀笔记后提示翻译功能。

```markdown
💡 **提示**: 如果需要批量翻译当前项目文档，可以使用：

    /repo-study translate

该命令会按任务分组并行派发 subagent，把文档翻译到对应 `*.zh.md` 文件（不修改原始 `*.md`）。
```

**注意事项**：
- 仅在用户使用中文提问时提示
- 如果用户使用英文提问，跳过此步骤
- 保持提示简洁，不干扰主要研究流程
