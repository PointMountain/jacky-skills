# 教程两阶段工作流

> 适用场景：研究的项目是工具/CLI/库，需要可执行教程时使用。
> 产出文件：`explorer/{repo-name}-how-to-use-guide.md`

## 为什么需要这个流程？

直接基于文档写教程 → 实测发现各种问题（API 失效、命令移除、网络不通）→ 反复重写浪费上下文。
两阶段分离后：配置引导不需要测（是 checklist），实测用 sub-agent 分而治之（不撑爆上下文）。

## Phase T1：环境配置引导（人工交互阶段）

> CC 角色：引导用户逐步完成，每步验证后再进入下一步。不要跳步。

1. **分析项目需要哪些配置步骤**：
   - 安装方式（npm/pip/brew 等）
   - Chrome 扩展/浏览器插件（如有）
   - Daemon/后台服务（如有）
   - 网站登录（需要 Cookie 的站点）
   - 网络环境确认（国内外 API 可用性）
   - 辅助工具（如 jq、curl 等）

2. **生成配置引导文档**，每个步骤包含：
   - 操作说明（告诉用户做什么）
   - 验证命令（如何确认这步做完了）
   - 完成标志（明确的通过条件）
   - 常见问题（排障指引）
   - 需要人工操作的步骤用 ⚠️ 标记

3. **底部放检查清单**，格式：

```markdown
## 配置完成检查清单

\`\`\`bash
# 逐项验证
xxx --version          # ☐ 安装成功
xxx doctor             # ☐ 服务运行中
xxx test-command       # ☐ 功能可用
\`\`\`

**全部打勾 → 配置完成，进入实测阶段！**
```

> ⚠️ **Checkpoint - Human-Verify** — 引导用户逐步完成每个配置步骤，全部通过后才能继续。

## Phase T2：逐章实测教程（自动化阶段）

> **前置条件**：Phase T1 检查清单全部通过。

### Step T2.1：拆分章节

将教程按**认证模式**或**功能模块**拆分为独立章节：

```
示例拆分（以 OpenCLI 为例）：
├── 第 1 章：公开数据获取        → public 认证
├── 第 2 章：输出格式控制        → public
├── 第 3 章：复用浏览器登录态     → cookie 认证
├── 第 4 章：手动浏览器控制       → browser 认证
├── 第 5 章：创建自定义适配器     → 自定义
└── 第 6 章：管道组合            → public
```

每章标注：
- 状态：`⚠️ 待实测`
- 认证模式：`public` / `cookie` / `browser` / 自定义
- 前置条件：依赖哪些章节

### Step T2.2：生成教程骨架

为每章生成**带占位符的教程骨架**：
- 命令全部写好（从 Phase 5 的研究结果来）
- 输出部分用 `（待实测填充）` 占位
- **不允许写"预期输出"**，所有数据必须实测

### Step T2.3：Sub-agent 逐章测试

```
主 Agent（编排器）
  │
  ├── Agent 1: 测试第 1 章（public API）
  ├── Agent 2: 测试第 2 章（输出格式）
  ├── Agent 3: 测试第 3 章（cookie 认证）
  │   （收集结果 → 更新文档）
  ├── Agent 4: 测试第 4 章（浏览器命令）
  ├── Agent 5: 测试第 5 章（自定义适配器）
  └── Agent 6: 测试第 6 章（管道组合）
      （收集结果 → 更新文档）
```

**并行策略**：3 章一组并行 → 收集结果 → 再 3 章并行。

**每个 sub-agent 的输入**：
- 本章要测试的命令列表
- 每条命令的超时时间
- 标准输出格式模板

**每个 sub-agent 的输出格式**：

```markdown
## 第 X 章实测报告

**测试时间**：YYYY-MM-DD HH:MM
**测试环境**：操作系统 / 运行时版本 / 项目版本

### 命令 1：xxx

\`\`\`bash
实际执行的命令
\`\`\`

**输出**：

\`\`\`
实际输出内容
\`\`\`

**状态**：✅ 通过 / ❌ 失败 / ⚠️ 需要人工干预
**备注**：（如有特殊情况）
```

### Step T2.4：合并结果

主 agent 收集所有 sub-agent 的测试报告后：
1. 替换各章的 `（待实测填充）` 为实际输出
2. 更新每章的状态标记（`⚠️ 待实测` → `✅ 已实测` / `❌ 有问题`）
3. 标注已知问题和替代方案
4. 更新文件头部的状态摘要

### Step T2.5：标注已知问题

```markdown
> **已知问题**：
> - `xxx hot`：偶发 Detached 错误，改用 `xxx news`
> - `yyy hot`：适配器 bug（未声明 strategy），改用 `zzz hot`
> - 自定义适配器示例 API 已失效，替换为替代 API
```

## 教程文件结构模板

```markdown
---
article_id: OBA-xxx
tags: [study-note, tutorial]
type: note
created_at: YYYY-MM-DD
updated_at: YYYY-MM-DD
---

# {项目名} 实战教程：从安装到精通

> **本文分两个阶段**：
> - **Phase 1**：环境配置引导（需要人工操作）
> - **Phase 2**：逐章实测教程（自动测试 + 生成教程）
>
> **必须严格按顺序执行**：Phase 1 全部完成后，才能进入 Phase 2。

---

# Phase 1：环境配置引导

（T1 产出的配置引导内容）

## 配置完成检查清单
（检查清单）

---

# Phase 2：逐章实测教程

> **前置条件**：Phase 1 检查清单全部通过。
> **当前状态**：✅ 全部 X 章已实测完成 / ⚠️ 待实测
> **实测环境**：操作系统 / 运行时版本 / 项目版本

## 第 1 章：xxx
（每章的内容，含实测输出）

## 第 X 章：xxx
...

## 收官：你学到了什么
（总结表格）

## 附录：命令速查表
（速查命令）
```

## 上下文管理策略

每个 sub-agent 只需关注本章节的命令，不需要了解其他章节的内容。这确保：
1. 每个 sub-agent 的上下文消耗最小
2. 即使某章失败，不影响其他章节的测试
3. 主 agent 只需做最终汇总，不被大量输出撑爆上下文
