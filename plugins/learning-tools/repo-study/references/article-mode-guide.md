# 技术展示文章模式指南

> 产出面向掘金/知乎等技术社区的展示文章，以研究者的第三人称视角，呈现项目的核心洞察和设计哲学。

## 适用场景

- 用户希望将研究成果对外分享
- 目标平台：掘金、知乎、CSDN、个人博客等技术社区
- 读者：有一定技术基础的开发者

## 前置条件

- 至少完成过一轮研究（`explorer/` 中有研究笔记）
- 优先使用已沉淀的笔记作为素材基础

---

## 一、工作流程

### Step 1: 研究素材收集

1. 读取 `explorer/` 和 `notes/` 目录下所有已有研究笔记
2. 读取源码中的 README、SKILL.md、CONTRIBUTING.md 等项目自述文档
3. 识别项目的「认知颠覆点」和「设计哲学」（从笔记中提炼）
4. 汇总素材清单：

```
素材清单：
- 研究笔记: {notes/ 下的文件列表}
- 项目文档: {README、SKILL.md 等关键内容}
- 认知颠覆点: {从笔记中提炼的核心洞察}
- 设计哲学: {作者的设计理念（如有）}
```

### Step 2: 启动文章生成 subagent

使用下方 §3 的 subagent prompt 模板，启动 Explore 类型 subagent 生成文章。

输入：
- 已有研究笔记内容摘要
- 项目自述文档关键内容
- 文章叙事模板

输出：
- 完整的面向技术社区的展示文章（Markdown）

### Step 3: 质量检查

对照 §4 的质量检查清单逐项验证：
- 叙事弧线是否完整（6 段式）
- 技术深度是否分层（入门 → 进阶 → 深入）
- 是否有研究者洞察（非纯客观转述）
- 代码块和架构图是否充分

### Step 4: 沉淀文章

1. 写入 `notes/{repo-name}-article.md`（非教程性质）
2. 更新 `.study-meta.json` 的 `topics[]` 进度（`articleCount++`）
3. 在文章末尾标注素材来源笔记

## 二、文章叙事模板（6 段式）

从优秀的开源项目展示文章中提炼，适配掘金/知乎技术博客风格。

### 第 1 段：惊艳开场

**目标**：用一个让人"不可能吧"的能力展示开头，吸引技术读者继续阅读。

**要素**：
- 具体场景 + 可量化数据
- 多个技术关键词并列（让技术人有画面感）
- 一句话引出项目名 + GitHub 链接

**模板**：
```markdown
# {项目名}：{一句话能力描述}

{一个令人惊讶的能力展示，具体到数字和场景}。

比如：{3-5 个具体使用场景并列，每个一行}。

{一句话总结，引出项目}。

> 项目地址：{GitHub URL}
```

**示例参考**：
> Web Access — 10 个子 Agent 同时操作小红书、微博、B站等 10 个不同平台，一次性打开 100 个网页，并行操作各平台界面，查阅内容、汇总报告。

### 第 2 段：痛点共鸣

**目标**：让读者感受到"我确实遇到过这个问题"，产生共鸣。

**要素**：
- 列举现有方案的不足（每个给具体失败场景）
- 附关键代码或配置说明痛点
- 用"理想方案应该怎样"收束（需求清单）
- 允许跳读提示

**模板**：
```markdown
## 现有方案为什么不够好？

想直接看安装和使用的可以跳到下一节 ⬇️

**{现有方案 A}**：{简述能力和不足}。

具体痛点：
- {痛点 1 + 具体失败场景}
- {痛点 2 + 具体失败场景}
- {痛点 3 + 具体失败场景}

**{现有方案 B}**：{简述能力和不足}。

{具体问题说明}

⬇️

理想的方案应该做到：

1. {需求 1}
2. {需求 2}
3. {需求 3}
4. {需求 4}
5. {需求 5}
```

### 第 3 段：快速上手

**目标**：让读者 5 分钟内能跑起来。

**要素**：
- 复制即用的安装命令（代码块）
- 3-5 个典型使用场景（每个一句话 + 代码示例）
- 架构概览图（ASCII/Mermaid）
- 注意事项

**模板**：
```markdown
## 快速安装和使用

### 安装

```bash
{安装命令}
```

### 基本使用

| 场景 | 命令/操作 | 说明 |
|------|----------|------|
| {场景 1} | `{命令}` | {说明} |
| {场景 2} | `{命令}` | {说明} |
| {场景 3} | `{命令}` | {说明} |

### 架构概览

{ASCII 架构图 或 Mermaid 图}

### 注意事项

- {注意 1}
- {注意 2}
```

### 第 4 段：设计哲学

**目标**：提炼出项目的核心设计理念，让读者获得"原来应该这样想"的洞察。

**要素**：
- 提出设计公式/理念（一句话概括）
- 分层展开（2-4 个维度）
- 每个维度：观点 → 代码证据 → 与替代方案对比
- 提炼出可迁移的设计思路

**模板**：
```markdown
## 设计哲学：{一句话公式}

研究了整个代码库后，我发现 {项目名} 的核心设计理念可以概括为：

> **{设计公式}**

具体来说：

### 1）{维度 1}
{观点说明}

{关键代码片段作为证据}

与 {替代方案} 相比，这种做法的好处是 {对比说明}。

### 2）{维度 2}
{观点说明}

{关键代码片段}

这种思路可以迁移到 {其他场景}。

### 3）{维度 3}
{观点说明}
```

### 第 5 段：技术亮点深挖

**目标**：展示 2-3 个最有"认知落差"的技术实现细节，证明深度。

**要素**：
- 选最有认知落差的技术点（不是最复杂的，而是最让人意外的）
- 关键代码片段（带中文注释）
- 核心数据流图
- 包含一个"容易忽略的机制陷阱"
- Before/After 代码对比

**模板**：
```markdown
## 技术亮点

### 亮点 1：{技术点名称}

{一句话说明为什么这个实现让人印象深刻}

**核心实现**：

```javascript
// {代码说明}
{关键代码片段，带中文注释}
```

**数据流**：

{ASCII 数据流图}

**Before vs After**：

| 场景 | ❌ 传统做法 | ✅ 本项目做法 |
|------|-----------|-------------|
| {场景} | {旧方式 + 代码} | {新方式 + 代码} |

### 亮点 2：{技术点名称}

{说明}

### 容易忽略的机制陷阱

{描述一个看起来简单但容易踩坑的实现细节}

{关键代码 + 分析}
```

### 第 6 段：开放讨论 + 总结

**目标**：引发评论区讨论，增加文章互动性。

**要素**：
- 提炼可迁移的技术洞察
- 提出开放性问题引发讨论
- 项目链接 + Star CTA

**模板**：
```markdown
## 总结与思考

研究了 {项目名} 之后，最让我印象深刻的是 {核心洞察}。

这种 {设计模式/思路} 其实不只适用于 {本项目场景}，还可以迁移到：
- {迁移场景 1}
- {迁移场景 2}

> 几个值得思考的问题：
> 1. {开放性问题 1}
> 2. {开放性问题 2}
> 3. {开放性问题 3}

欢迎在评论区讨论你的看法 👇

---

项目地址：{GitHub URL}

如果这篇文章对你有帮助，欢迎 Star ⭐ 和分享。
```

## 三、Subagent Prompt 模板

```
你是一位面向技术社区的内容创作者。请根据以下研究素材，生成一篇面向掘金/知乎等技术社区的技术展示文章。

**项目名称**: {repo-name}
**项目地址**: {GitHub URL}
**研究素材**: {已有研究笔记内容摘要}
**项目文档**: {README/SKILL.md 关键内容}
**目标读者**: 有一定技术基础的开发者，对 {项目领域} 感兴趣

### 视角定位

以**深度研究者的第三人称视角**写作：
- 用"研究了这个项目后"、"让人印象深刻的是..."的角度
- 不假装是原作者，但可以提炼和总结作者的设计哲学
- 可以加入自己作为研究者的洞察和评价

### 叙事结构（必须包含 6 个阶段）

1. **惊艳开场** — 用具体场景/数字展示项目能力，引出项目名
2. **痛点共鸣** — 对比现有方案不足，列出理想方案需求
3. **快速上手** — 安装命令 + 使用场景 + 架构概览图
4. **设计哲学** — 提炼一句话设计公式，分层展开
5. **技术亮点** — 2-3 个有深度的实现剖析（含代码）
6. **开放讨论** — 提炼洞察 + 开放性问题 + 项目链接

### 技术深度要求（适配掘金/知乎）

- 代码块：关键实现必须有完整代码片段和中文注释
- 原理分析：不只说"怎么用"，要说清"为什么这样设计"
- 架构图：用 ASCII 或 Mermaid 画核心架构
- Before/After 对比：展示有无这个方案的差异

### 必须包含的内容

- 开头用具体场景/数字展示项目能力
- 对比现有方案的不足（附具体失败场景）
- 提炼项目的设计哲学（一句话公式 + 分层展开）
- 2-3 个有深度的技术实现剖析（含代码引用）
- 结尾提出开放性问题或讨论点

### 风格要求

- 技术自信但有理有据
- 有个人洞察和评价，不是纯客观转述
- 用具体代码/场景替代抽象描述
- 适当使用 emoji 和 ⬇️ 箭头引导阅读流
- 代码块使用 ``` 标注语言类型，注释使用中文

### 避免事项

- 不要写成纯技术文档或 API 说明
- 不要用"本文将介绍..."开头
- 不要罗列所有功能，只讲最有洞察的部分
- 不要缺少个人评价和设计思考

### 输出格式

完整的 Markdown 文章，可直接发布到掘金/知乎。字数 3000-5000 字。
```

## 四、文章质量检查清单

生成文章后，逐项验证：

### 结构完整性
- [ ] 是否包含完整的 6 段叙事弧线？
- [ ] 开场是否有具体的、可量化的能力展示？
- [ ] 痛点是否对比了至少 1 个现有方案的不足？
- [ ] 是否有"复制即用"的安装方式（代码块）？

### 技术深度
- [ ] 是否提出了一个设计哲学/理念（一句话公式）？
- [ ] 是否有 2-3 个有深度的技术亮点（含代码分析）？
- [ ] 是否有架构图或数据流图（ASCII/Mermaid）？
- [ ] 是否有 Before/After 对比？
- [ ] 代码块是否标注语言类型并有中文注释？

### 写作质量
- [ ] 语气是否自然、有研究者洞察（非纯技术文档）？
- [ ] 是否使用了具体代码/场景举例（非抽象描述）？
- [ ] 技术深度是否分层（入门能看懂 → 资深能深入）？
- [ ] 是否有跳读提示（"想直接用的跳到..."）？

### 互动与收尾
- [ ] 结尾是否有开放性问题引发讨论？
- [ ] 是否包含 GitHub 链接和 Star CTA？

## 五、风格要素速查

| 要素 | 具体做法 | 掘金/知乎适配 |
|------|---------|-------------|
| **开头钩子** | 具体数字 + 技术关键词开场 | "10 个 sub-agent...CDP 协议...100 个网页" |
| **代码证据** | 关键论点配代码片段 | 核心架构代码、关键配置、对比代码 |
| **对比框架** | 竞品 → 痛点 → 理想 → 目标方案 | 表格形式，竞品按维度对比 |
| **架构可视化** | ASCII 图 / Mermaid 图 | 数据流图、模块关系图 |
| **渐进披露** | 提供跳读入口 | "想直接用的跳到安装章节" |
| **具体 > 抽象** | 先给场景/代码再给概念 | 先展示效果再讲原理 |
| **Before/After** | 量化差异 | 代码对比表格 |
| **设计洞察** | 提炼可迁移的设计思路 | "这个模式可以用于..." |
| **开放讨论** | 提出有争议性的技术问题 | "你觉得这种方案和 XX 相比呢？" |
| **⬇️ 箭头** | 标记段落转折 | 段落之间用 ⬇️ 引导视线 |

## 六、产出文件格式

文件路径：`notes/{repo-name}-article.md`

```markdown
---
title: "{项目名}：{一句话能力描述}"
date: "{生成日期}"
source_notes:
  - "{素材笔记 1 路径}"
  - "{素材笔记 2 路径}"
tags: ["技术展示", "{项目领域}"]
---

{文章正文}
```
